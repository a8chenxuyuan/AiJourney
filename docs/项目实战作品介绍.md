# agent1旅行 — 智能旅行规划系统实战作品介绍

> 本文档用于求职/作品展示，可直接复制到飞书文档，建议设置为「组织内成员可阅读」或「互联网上获得链接的人可阅读」。

## 一、作品概述

**作品名称**：agent1旅行 — 智能旅行规划系统

**作品定位**：一款面向 C 端用户的 AI 旅行规划助手。用户输入目的地、日期、偏好、必去景点后，系统自动生成一份包含景点、酒店、餐饮、路线、预算、天气的多日行程攻略。

**核心亮点**：

- 基于真实 POI 数据（高德地图），拒绝 AI 编造景点和餐厅
- 多 Agent 协作完成意图理解、POI 检索、路线规划、预算统计
- SSE 实时推送每个 Agent 的执行进度
- 行程支持反馈迭代，自动生成版本链和差异摘要
- 三层记忆系统（短期对话、中期偏好、长期事件记忆）

**技术栈**：Vue 3 + TypeScript + Vite + Ant Design Vue + FastAPI + SQLAlchemy(async) + Pydantic v2 + LangChain + DashScope + 高德地图 API + Qdrant

## 二、需求分析

### 2.1 用户痛点

| 痛点 | 具体表现 |
|---|---|
| 信息分散 | 做攻略需要在携程、大众点评、高德、小红书之间反复切换 |
| 内容虚假 | 部分 AI 工具会编造景点、餐厅，用户到了现场发现不存在 |
| 个性化不足 | 模板化攻略无法结合用户的预算、偏好、必去景点 |
| 无法迭代 | 生成的行程不满意，只能重新填写一遍需求 |
| 缺乏实时性 | 天气、营业时间、路线距离等关键信息缺失 |

### 2.2 目标用户

- 年轻人/学生党：预算敏感，喜欢特种兵或休闲游
- 家庭出行：需要兼顾老人小孩，重视路线合理性
- 短途周末游：时间有限，希望快速得到可执行的攻略

### 2.3 核心需求

1. **真实可靠**：景点、酒店、餐厅必须来自真实地图 POI
2. **个性化**：支持预算等级、旅行偏好、必去景点、饮食禁忌
3. **可执行**：包含每日路线、交通方式、预估费用、营业时间
4. **可迭代**：用户可以对某一天的安排提反馈，系统重新生成并高亮差异
5. **实时反馈**：生成过程可见，每个 Agent 的进度实时展示

## 三、产品设计思路（聚焦 Agent）

### 3.1 整体架构：以多 Agent 协作为核心

本系统的核心设计不是传统的前后端 CRUD，而是一个**围绕多 Agent 协作构建的智能流水线**。前端负责收集需求和展示结果，后端负责调度和持久化，真正的「大脑」是 11 个顺序执行的 Agent 节点。

```
用户前端（Vue 3）
    ↓ HTTP / SSE
后端 API（FastAPI）
    ↓ 启动后台任务
多 Agent 执行图（11 个节点顺序执行）
    ↓ 调用外部工具
高德地图 API / 百炼 LLM / Qdrant 向量库
    ↓ 写入
SQLite 数据库
```

**设计哲学**：把一次旅行规划拆分成多个专业子任务，每个 Agent 只负责一件事，通过共享 State 协作完成最终行程。这种方式比单一 Prompt 生成全行程更稳定、更可解释、更容易调试。

### 3.2 Agent 执行流程

一次完整的规划会依次执行以下节点：

```
intent_agent → attraction_agent → weather_agent → hotel_agent
→ food_agent → rag_agent → route_agent → planner_agent
→ budget_agent → human_in_the_loop → finalize
```

每个 Agent 的输出会写入共享 State，下一个 Agent 从 State 中读取所需信息。

**示例数据流**：

1. `intent_agent` 解析出「城市=湛江，偏好=美食，必去=湖光岩」
2. `attraction_agent` 基于城市和 must_visit 搜索真实景点
3. `food_agent` 基于城市+偏好搜索真实餐厅
4. `route_agent` 计算景点之间的距离和通行时间
5. `planner_agent` 综合以上所有信息，生成每日行程
6. `finalize` 把结果落库，并推送给前端

### 3.3 关键产品决策

| 决策 | 说明 |
|---|---|
| 编排式 Multi-Agent | 11 个 Agent 按固定流程协作，不是单一 Main Agent 指挥 Sub Agent |
| 真实 POI 驱动 | 景点、酒店、餐厅全部来自高德地图，禁止 AI 编造 |
| 共享 State 机制 | Agent 之间通过统一 State 传递数据，不是简单链式输入输出 |
| 手动顺序调度 Agent | 规避 LangGraph Checkpoint 序列化大 State 时的卡顿问题 |
| 反馈不立即触发重算 | 让用户可以一次性提交多条反馈，再统一处理 |
| per-plan 互斥锁 | 同一行程同时只允许一个修订任务，避免数据冲突 |
| diff_summary 高亮差异 | 让用户感知到「这次到底改了什么」 |

## 四、技术实现方案（聚焦 Agent 与知识库）

### 4.1 前端与后端（简要说明）

**前端**：Vue 3 + TypeScript + Vite + Ant Design Vue + 高德地图 JS API。核心页面包括需求表单、SSE 进度页、结果展示页、个人中心。

**后端**：FastAPI + Pydantic v2 + SQLAlchemy 2.0(async) + SQLite。主要职责是接收请求、启动 Agent 后台任务、提供 SSE 流、持久化行程数据。

### 4.2 多 Agent 协作设计

#### 4.2.1 为什么是编排式 Multi-Agent？

本项目没有采用「一个 Main Agent 动态调用多个 Sub Agent」的模式，而是采用**编排式（Orchestrated）Multi-Agent**：

- 11 个 Agent 按固定流程顺序执行
- 每个 Agent 有明确的输入、输出和职责边界
- 通过共享 State 传递数据

**优势**：

- 流程可控：每个步骤的输出都可以被校验和观察
- 调试方便：哪个 Agent 出错，日志里一目了然
- 扩展容易：新增 Agent 只需要插入到合适的位置

#### 4.2.2 11 个 Agent 的详细职责

```
intent_agent → attraction_agent → weather_agent → hotel_agent
→ food_agent → rag_agent → route_agent → planner_agent
→ budget_agent → human_in_the_loop → finalize
```

| Agent | 输入 | 输出 | 核心功能 |
|---|---|---|---|
| IntentAgent | 用户表单 | 结构化意图 | 把自然语言需求解析为城市、日期、偏好、must_visit 等字段 |
| AttractionAgent | 城市、偏好、must_visit | 景点列表 | 高德 POI 搜索，代码级强制包含 must_visit 景点 |
| WeatherAgent | 城市、日期 | 天气预报 | 查询旅行期间每日天气 |
| HotelAgent | 城市、住宿偏好 | 酒店列表 | 搜索酒店 POI |
| FoodAgent | 城市、偏好 | 餐厅列表 | 搜索真实餐厅，包含图片、电话、营业时间、地址 |
| RAGAgent | 城市、偏好 | 攻略文本 | 从知识库检索城市攻略或景点背景 |
| RouteAgent | 景点列表 | 路线矩阵 | 计算景点两两之间的距离和通行时间 |
| PlannerAgent | 所有前置结果 | 完整行程 | 核心节点，LLM 生成每日景点、餐饮、酒店安排 |
| BudgetAgent | 完整行程 | 预算统计 | 统计门票、餐饮、住宿、交通费用 |
| HumanInTheLoop | 行程 | 确认/修改 | 当前自动放行，预留人工审核扩展点 |
| Finalize | 最终行程 | 数据库记录 | 落库、维护版本链、计算差异、固化记忆 |

#### 4.2.3 Agent 之间如何沟通？

所有 Agent 共享同一个 `TravelPlanningState`（一个 Python 字典）：

```
State = {
    request: 用户原始请求,
    intent_analysis: 意图分析结果,
    attractions: 景点列表,
    hotels: 酒店列表,
    restaurants: 餐厅列表,
    weather: 天气信息,
    route_matrix: 路线矩阵,
    rag_context: 检索到的知识,
    final_plan: 最终行程,
    logs: 执行日志,
    ...
}
```

每个 Agent 从 State 中读取自己需要的数据，处理完成后把结果写回 State。下一个 Agent 继续读取更新后的 State。

**与链式调用的区别**：不是「A 的输出直接作为 B 的输入」，而是「A 把结果放到公共白板上，B 从白板上取自己需要的部分」。

#### 4.2.4 调度方式：手动顺序执行

项目早期使用 LangGraph 的 `ainvoke` 自动调度，但当 State 里包含大量 Pydantic 对象和路线矩阵时，LangGraph 的 Checkpoint 序列化机制会卡住。因此把调度层改成手动 `await node_func(state)`，但保留了 StateGraph 的节点定义方式，方便后续恢复自动调度。

### 4.3 Agent 的工具系统

每个 Agent 通过调用外部工具完成具体任务：

| 工具 | 功能 | 使用 Agent |
|---|---|---|
| `search_attractions` | 高德 POI 搜索景点 | AttractionAgent |
| `search_hotels` | 高德 POI 搜索酒店 | HotelAgent |
| `search_restaurants` | 高德 POI 搜索餐厅 | FoodAgent |
| `get_weather` | 查询天气 | WeatherAgent |
| `get_route` | 计算两点路线 | RouteAgent |
| `search_rag_context` | 从 Qdrant 检索知识 | RAGAgent |
| `batch_search_or_fetch` | 百度百科补景点背景 | AttractionAgent |

**工具调用方式**：不是 ReAct 推理，而是「LLM 结构化生成 + 代码主动调用工具」。Agent 内部用代码决定调用哪些工具，把工具结果整理后写入 State。

### 4.4 Prompt 设计

- **Prompt 模板集中管理**：所有 Agent 的 Prompt 写在 `prompts.py` 中
- **JSON 输出约束**：每个 Agent 要求 LLM 输出严格 JSON，方便 Pydantic 校验
- **关键约束反复强调**：例如 PlannerAgent 的 Prompt 里明确要求「每天三餐必须从候选餐厅列表中选取真实店铺」
- **POI 摘要机制**：把高德返回的大段 POI 信息压缩成关键字段，让 Prompt 控制在 5000 字符以内
- **占位符转义**：Python f-string 中遇到 JSON 花括号时，用 `{{` 和 `}}` 转义

### 4.5 记忆系统设计

三层记忆：

| 层级 | 存储 | 内容 | 使用时机 |
|---|---|---|---|
| 短期记忆 | State | 当前行程的上下文 | 单次规划内传递 |
| 中期记忆 | SQLite `user_preferences` | 结构化偏好（预算、口味、交通方式） | 每次新建行程时 IntentAgent 读取 |
| 长期记忆 | SQLite `user_memories` + Qdrant | 具体事件（如 dislike 某景点原因） | 按语义相似度召回 |

**中期记忆**是结构化键值对，直接查表全量读取写进 Prompt。

**长期记忆**是非结构化文本，通过 Embedding 后存入 Qdrant，按当前查询语义召回最相关的几条。

### 4.6 RAG 与知识库设计

#### 4.6.1 知识库的定位

知识库的作用不是替代 LLM 的推理能力，而是**给 LLM 提供真实、准确、可引用的背景信息**，避免它编造景点历史、文化内涵、城市特色。

#### 4.6.2 知识库的两条数据路径

| 路径 | 目标 | 数据来源 | 使用方式 | 缓存策略 |
|---|---|---|---|---|
| 景点背景知识 | 为每个景点生成真实描述 | 百度百科摘要 | AttractionAgent 按需抓取 | 先查缓存/Qdrant，未命中则抓百度百科，回写缓存 |
| 城市攻略 | 为 PlannerAgent 提供城市整体游玩建议 | 批量导入的优质攻略文档 | RAGAgent 从 Qdrant 检索 | 批量导入，不主动抓取 |

#### 4.6.3 知识库技术架构

```
用户查询 / Agent 需求
    ↓
Embedding 模型（BAAI/bge-large-zh-v1.5）
    ↓
Qdrant 向量库
    ↓
语义相似度 Top-K 检索
    ↓
召回文本片段
    ↓
写入 Prompt 上下文
```

**数据预处理**：

- 文本分块（Chunk）：把长文档切分成适合 Embedding 的小段
- Embedding：把文本转换为向量
- 元数据：每个向量携带来源、类型、创建时间等标签

#### 4.6.4 知识库在 Agent 中的使用

| Agent | 使用知识库的方式 |
|---|---|
| AttractionAgent | 为每个景点补充背景描述，让景点介绍更生动 |
| RAGAgent | 检索城市攻略，为 PlannerAgent 提供「这座城市应该怎么玩」的参考 |
| PlannerAgent | 把检索到的知识作为上下文，生成更符合城市特色的行程 |

#### 4.6.5 知识库与记忆系统的关联

| 维度 | 知识库 | 记忆系统 |
|---|---|---|
| 内容 | 公共知识（景点、城市、攻略） | 用户个人偏好和经历 |
| 更新频率 | 低频，批量导入 | 高频，每次反馈都可能更新 |
| 检索方式 | 向量语义检索 | 中期记忆精确读取 + 长期记忆向量检索 |
| 使用对象 | 所有用户共享 | 仅当前用户使用 |
| 典型场景 | 回答「北京有什么好玩的」 | 回答「这个用户不喜欢爬山」 |

#### 4.6.6 降级与容错

- Qdrant 未启动时，RAGService 自动降级为内存模式
- 景点背景知识检索失败时，返回空字符串，不影响主流程
- 百度百科抓取失败时，使用景点基础信息作为描述

### 4.7 关键技术难点

| 难点 | 解决方案 |
|---|---|
| LangGraph 序列化大 State 卡住 | 改成手动 `await node_func(state)`，保留 StateGraph 定义方式 |
| LLM 输出字段类型不稳定 | Pydantic 校验 + 自动清洗（如字符串 cost 转数字） |
| POI 信息过多导致 Prompt 过长 | `_summarize_poi_for_prompt` 摘要机制，控制在 5000 字符以内 |
| 同一 plan 多次反馈导致冲突 | per-plan 互斥锁（`_revision_locks` + `_revision_running`） |
| 向量库未启动 | RAGService 自动降级为内存模式 |
