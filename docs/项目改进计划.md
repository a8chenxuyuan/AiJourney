# agent1旅行 项目改进计划

> 本文档记录项目从“能跑通”到“好用”的演进过程。每一版都围绕一个核心问题：用户第一次生成的行程往往无法一次满意，怎么让它更真实、更好看、更容易修改？
>
> 建议先读每版的“要解决什么问题”和“改了什么”，技术实现细节可以后续再看。
>
> **注**：文中提到的文件路径（如 `agents/nodes.py`、`routes/trip.py`、`views/Result.vue`、`api/trip.ts`）均为对应版本当时的路径；重构后部分文件已拆分/移动（如 `nodes.py` → `nodes/` 包、前端 views/api 按域分组），最新结构见 `项目结构与实现说明.md`。

---

## 项目整体演进路线

1. **版本 1.0**：先让系统能把一条完整行程生成出来，但结果像文字清单，体验粗糙。
2. **版本 1.1**：让结果页变成“卡片式攻略”，带上图片、评分、地图，让用户一眼看懂。
3. **版本 1.2/1.3**：让景点介绍和餐厅信息来自真实数据，不再编造。
4. **版本 1.4**：支持用户对每一天提修改意见，系统根据所有反馈重新生成，并记住用户的长期偏好。

## 版本 1.0：基础行程规划

### 这个阶段实现了什么

用户注册登录后，填写目的地、日期、交通/住宿偏好、必去景点，系统会调用 AI 生成一份多日行程。结果包含：

- 每天去哪些景点、停留多久
- 每天三餐和住宿
- 预算估算
- 天气信息

前端有创建页、结果页，规划过程中会通过 SSE 实时推送进度。

### 当时的核心问题

1. **结果页太简陋**：只有文字列表，没有图片、评分、链接，用户很难判断景点或餐厅靠不靠谱。
2. **地图是摆设**：不管目的地是哪里，地图都默认显示北京，也不会标出当天景点。
3. **进度不真实**：前端进度条是模拟的，不能反映后端实际执行到了哪一步。
4. **部分数据是编的**：餐厅有时只是“附近餐厅”这种通用名称，景点介绍也比较单薄。

## 版本 1.1：让行程结果“看得见、信得过”

### 要解决什么问题

用户打开结果页后，第一眼看不到有用的参考信息。我们要把行程从“文字清单”升级为“带图、带评分、带地图的卡片式攻略”，并且让信息来自真实的高德 POI，而不是 AI 凭空生成。

### 核心改动

1. **结果页卡片化**
   - 景点、餐厅、酒店都用卡片展示，左图右信息。
   - 显示评分、电话、营业时间、地址、高德详情链接。

2. **地图真正可用**
   - 地图中心自动定位到目的地城市。
   - 每天右侧显示当天景点在地图上的标记。

3. **后端能拿到更丰富的真实数据**
   - 调用高德接口时请求完整字段（图片、评分、电话等）。
   - 对返回结果做解析和补全，给每个 POI 生成标签、建议游玩时长等。

4. **更稳定的字段解析**
   - 餐饮人均消费有时被 AI 写成“20元”这种字符串，现在自动提取数字，避免解析失败。

```python
@field_validator("estimated_cost", mode="before")
@classmethod
def parse_estimated_cost(cls, value):
    if value is None:
        return None
    if isinstance(value, (int, float)):
        return float(value)
    if isinstance(value, str):
        import re
        numbers = re.findall(r"\d+(?:\.\d+)?", value)
        if numbers:
            return float(numbers[0])
        return None
    return value
```

#### 3. 修改 Agent 工具函数，组装 enrichment 字段

**`backend/app/agents/tools.py`：**
- `_enrich_attraction`：根据 POI 类型推断标签和游玩时长，构造 `detail_url`、`phone`、`business_hours`、默认描述。
- `_enrich_hotel`：根据酒店名称关键词估算每晚价格，补充 `detail_url`、`phone`、`business_hours`、默认描述。

**关键代码：**
```python
def _enrich_attraction(poi: Dict[str, Any]) -> Dict[str, Any]:
    typecode = poi.get("typecode", "")
    name = poi.get("name", "")

    if typecode.startswith("110000"):
        tags = ["风景", "观光"]
        duration = "2.5 小时"
    elif typecode.startswith("110100"):
        tags = ["公园", "休闲"]
        duration = "2 小时"
    elif typecode.startswith("140000") or "博物馆" in name:
        tags = ["文化", "博物馆"]
        duration = "2.5 小时"
    elif typecode.startswith("060000") or "商场" in name or "购物" in name:
        tags = ["购物", "休闲"]
        duration = "1.5 小时"
    elif typecode.startswith("050000") or "美食" in name or "街" in name:
        tags = ["美食", "街拍"]
        duration = "1.5 小时"
    else:
        tags = ["观光"]
        duration = "2 小时"

    detail_url = f"https://ditu.amap.com/search?query={name}"

    return {
        **poi,
        "tags": tags,
        "duration": duration,
        "description": f"{name} 是 {poi.get('type', '当地')} 的热门地点，地址：{poi.get('address') or '详见地图'}。",
        "detail_url": detail_url,
        "phone": poi.get("tel"),
        "business_hours": poi.get("business_hours"),
    }
```

**4.3 路线节点（`route_agent_node`）并行计算并返回 polyline**
- 使用 `asyncio.gather` 并行计算所有景点对的路线。

- 返回结果包含 `polyline` 字段。

**4.4 新增地图辅助函数**
- `_encode_polyline(points)`：将经纬度点列表编码为 `"lon,lat;lon,lat"` 字符串。
- `_calculate_center(locations)`：计算一组坐标的几何中心点。
- `_build_day_route_polyline(attractions, route_matrix)`：根据当天景点顺序拼接路线 polyline。
- `_enrich_day_plan_with_map_data(day, route_matrix)`：为单日行程补充 `map_center` 和 `route_polyline`。

**关键代码：**
```python
def _enrich_day_plan_with_map_data(
    day: DayPlan,
    route_matrix: Dict[str, Any]
) -> None:
    if day.attractions:
        locations = [a.location for a in day.attractions if a.location]
        day.map_center = _calculate_center(locations)
        day.route_polyline = _build_day_route_polyline(day.attractions, route_matrix)
```

**4.5 规划节点（`planner_agent_node`）调用地图数据补充**
在补齐基础字段后，对每个 `DayPlan` 调用 `_enrich_day_plan_with_map_data`：
```python
# 步骤 5：补充每日地图数据

for day in plan.day_plans:
    _enrich_day_plan_with_map_data(day, route_matrix)
```

**4.6 兜底计划（`_build_fallback_plan`）同样补充地图数据**
无论是有景点还是无景点情况，构造 `DayPlan` 后都调用 `_enrich_day_plan_with_map_data(day_plan, state.get("route_matrix", {}))`。

```typescript
const parsePolyline = (polyline: string): any[] => {
  if (!polyline || !AMap) return []
  const points: any[] = []
  for (const segment of polyline.split(';')) {
    const parts = segment.split(',')
    if (parts.length !== 2) continue
    const lon = parseFloat(parts[0])
    const lat = parseFloat(parts[1])
    if (!isNaN(lon) && !isNaN(lat)) {
      points.push(new AMap.LngLat(lon, lat))
    }
  }
  return points
}

const drawPolyline = (polyline: string) => {
  if (!amapInstance || !AMap || !polyline) return
  const path = parsePolyline(polyline)
  if (path.length < 2) return
  const routeLine = new AMap.Polyline({
    path,
    strokeColor: '#1890ff',
    strokeWeight: 4,
    strokeOpacity: 0.8,
    showDir: true
  })
  amapInstance.add(routeLine)
}
```

## 版本 1.2：景点背景不再单薄

### 与上一版的区别

版本 1.1 让结果页变得好看，但景点介绍仍然比较单薄，像“某某是热门地点，地址详见地图”这种套话。用户真正想了解的是：这个景点有什么历史、看什么、怎么玩。

### 这一版怎么做

我们给每个景点增加了一段真实的背景介绍，来源是百度百科。为了避免每次都去爬网页，引入了“先查缓存，没有再搜，搜完存起来”的机制：

1. 第一次搜索某个景点时，去百度百科抓取摘要，并存入向量库。
2. 以后再规划同一个城市或同一个景点时，直接从缓存里取，速度更快。
3. 这样知识库会随着使用次数自动变厚，不需要人工提前维护。

**新增方法：**
```python
async def search_or_fetch(
    self,
    query: str,
    city: Optional[str] = None,
    source_type: str = "attraction",
    external_fetcher: Optional[Callable] = None,
    min_score: float = 0.75
) -> Dict[str, Any]:
    """
    先查缓存，未命中则调外部搜索，结果存入缓存后返回。

    流程：
    1. 先查本地向量库缓存
    2. 缓存命中且置信度 >= min_score → 直接返回
    3. 缓存未命中 → 调外部搜索（默认百度百科）
    4. 外部搜索结果存入向量库缓存
    5. 返回结果

    Returns:
        {
            "content": "检索到的文本内容",
            "title": "标题",
            "score": 1.0,
            "from_cache": False,
            "source_type": "attraction",
            "url": "百科链接"
        }
    """

async def batch_search_or_fetch(self, queries: List[str], ...) -> List[Dict]:
    """批量搜索：先查缓存，未命中则外部搜索"""
```

**设计理念：**
- **搜索优先**：优先从缓存获取，避免重复外部请求
- **渐进积累**：每次外部搜索结果都存入缓存，知识库自动生长
- **置信度控制**：只有高置信度的缓存结果才直接返回，否则重新搜索

### 已修复问题

#### 问题 1：用户指定的"必去景点"未出现在行程中

**现象：**
- 用户在表单中填写了必去景点（如"金沙湾"、"赤坎老街"）
- 但生成的行程中没有安排这些景点，反而出现了"天鹅湖"、"肯德基"等与偏好无关的 POI

**根因分析：**
1. `attraction_agent_node` 将 `must_visit` 和 `preferences` 混在一起作为搜索关键词，且只取前 4 个搜索，必去景点可能因 set 去重后顺序靠后而未被搜索
2. `PlannerAgent` 的 Prompt 没有明确要求必须包含 `must_visit` 景点
3. LLM 即使看到 `must_visit`，也可能因上下文过长或"创造性"安排而遗漏

**修复方案：**
1. **优先单独搜索必去景点**：在 `attraction_agent_node` 中新增"步骤 2"，对每个 `must_visit` 单独调用 `search_attractions`，确保必去景点排在候选列表最前面
2. **Prompt 强制约束**：在 `PLANNER_SYSTEM_PROMPT` 中增加明确要求："must_visit（必去景点）必须全部安排在行程中，不能遗漏"
3. **代码层强制兜底**：在 `planner_agent_node` 中新增校验逻辑，LLM 输出后检查是否包含所有 `must_visit`，缺失则自动从候选景点中补入；候选列表也没有时构造占位景点

**涉及文件：**
- `backend/app/agents/nodes.py`
- `backend/app/agents/prompts.py`

**关键代码（强制校验）：**
```python
must_visit_names = [m.strip() for m in (intent.must_visit if intent else []) if m.strip()]
if must_visit_names:
    planned_names = set()
    for day in plan.day_plans:
        for a in day.attractions:
            planned_names.add(a.name.strip())

    missing_must_visit = [mv for mv in must_visit_names if not any(mv in pn or pn in mv for pn in planned_names)]

    for mv_name in missing_must_visit:
        # 从候选景点中查找
        matched = next((cand for cand in state["attractions"] if mv_name in cand.name or cand.name in mv_name), None)
        if matched is None:
            # 构造占位景点
            matched = Attraction(
                id=f"attr_must_{uuid.uuid4().hex[:8]}",
                name=mv_name,
                location=default_location,
                description=f"{mv_name} 是您指定的必去景点。",
                duration="2 小时",
                tags=["必去景点"]
            )
        # 插入到景点最少的那一天
        target_day = min(plan.day_plans, key=lambda d: len(d.attractions))
        target_day.attractions.append(matched)
```

## 版本 1.4：行程可以反复修改，系统会记住你的偏好

### 与上一版的区别

以前行程生成后用户只能看，不满意也只能重新填表再生成一次。实际旅行规划中，用户往往会有一些零散想法：
- “第二天太满了”
- “第三天中午想吃海鲜”
- “我不想爬山”

这些意见如果能让系统直接改，而不是从头再来，体验会好很多。

### 这一版怎么做

我们在结果页给每一天都增加了反馈入口，用户可以：

1. **提修改意见**：选择快捷标签 + 填写具体想法，还可以顺手搜索一个想替换的景点/餐厅作为候选。
2. **系统决定怎么改**：小改动（比如只换一家餐厅）走“局部补丁”，只改那一天；大改动（比如整体节奏、偏好变化）走“完整重排”，重新生成整个行程。
3. **改完形成新版本**：每次修改都会生成一个新版行程，旧版本保留在“修改记录”里，但页面上始终只显示最新版。
4. **反馈可以撤回/编辑**：写错了可以撤回，想补充可以编辑，系统只基于当前有效的反馈继续规划。
5. **记住你的偏好**：如果用户多次表示“不喜欢太满的行程”“喜欢吃海鲜”，系统会把这些偏好记下来，下次规划时自动生效。

```python
async def consolidate_memory(self, session, user_id, city, structured_feedback, raw_text):
    preference = await self.get_or_create_preference(session, user_id)
    current_prefs = json.loads(preference.preference_data) if preference.preference_data else {}

    # 1. 更新抽象偏好
    for signal in structured_feedback.preference_signals or []:
        sig_type = signal.get("type")
        value = signal.get("value")
        if sig_type and value is not None:
            current_prefs[sig_type] = value

    # 2. 写入具体事件记忆
    for action in structured_feedback.actions:
        memory_type = self._action_to_memory_type(action.get("type"))
        if memory_type is None:
            continue
        memory = db_models.UserMemory(
            user_id=user_id,
            memory_type=memory_type,
            entity_name=action.get("name") or action.get("target_name"),
            city=city,
            sentiment="negative" if "dislike" in memory_type or "remove" in memory_type else "positive",
            reason=action.get("reason", ""),
            context=f"用户反馈：{raw_text}"
        )
        session.add(memory)
        await session.flush()
        await self._sync_memory_to_qdrant(memory)

    preference.preference_data = json.dumps(current_prefs, ensure_ascii=False)
    await session.flush()
```

#### 修复 11：Pydantic 严格模式拒绝 null，导致 v2 创建失败

**发生了什么？**
每次跑"重新生成行程"时，PlannerAgent 节点会调用大模型（百炼 API）让 LLM 输出一段 JSON 格式的行程。后端要把这段 JSON 转成 Pydantic 对象才能保存到数据库。可是日志里常常冒出一长串红色错误：
```
Input should be a valid number, input_value=None, input_type=NoneType
```
一次就刷 40 多条，看起来吓人。

**为什么会这样？**
Pydantic v2 默认是"严格模式"——你声明某个字段是 `float` 类型（比如"总预算 = 0.0"），LLM 输出 `null` 就会直接报错。
而 LLM 经常把"用户没填的字段"写为 `null`，比如用户没写景点预算，它就给你 `"attractions": null`。

**怎么修好的？**
1. 把 `Budget` 模型里所有 `float = 0.0` 的字段都改成 `Optional[float] = 0.0`，**允许 None**。
2. 在 [json_parser.py](file:///d:/agent1/backend/app/utils/json_parser.py#L144-L158) 里加第三次"宽松模式"兜底：解析失败时把 None 按字段名规则替换为默认值（涉及价格/费用的填 `0.0`、涉及列表的填 `[]`），再校验一次。

**效果**：之前 100% 必触发 42 个错误，现在基本 0 错误，任务耗时也从 6 分多降到 4 分钟左右。

#### 修复 10：SSE 跳回结果页时前端不刷新

**发生了什么？**
"重新生成行程"跑完后，前端自动跳到 `/result/{id}` 页面，按理说应该看到全新的 v2 行程。可是用户反复反馈"还是 v1 的内容"，刷新浏览器才看到 v2。

**为什么会这样？**
Vue Router 在跳转时有个特性：**如果跳转前后是同一个组件（比如都叫 Result.vue），它会复用这个组件实例**，不会重新触发 `onMounted`。
我在 Result.vue 里加了 `watch(() => route.params.id)` 想监测路由变化，可是因为组件被复用了，watch 也没生效。
根本原因是用户经常在 regenerate 跑完前就回到 Result.vue，**那时候 v2 还没落到数据库**，后来任务跑完了 v2 落库了，但前端一直显示早先的 v1 状态。

**怎么修好的？**
在 [Planning.vue](file:///d:/agent1/frontend/src/views/Planning.vue#L57-L62) 把跳转从 `router.push` 改成 `window.location.href = '/result/{id}?refresh=' + Date.now()`。这样浏览器会**强制整页刷新**，彻底绕开 Vue Router 复用组件的问题。

**效果**：用户点完按钮，无论中间怎么切页面，最后跳回时一定看到最新的 v2。

#### 修复 9：前端"修改了 N 处"高亮框

老版本前端在 Result.vue 只能看到一个"v1 标签"，但下面展开的还是 v1 的内容。如果 v2 改了 1 处、用户又不知道改了 1 处，那感觉就是"没变"。

#### 修复 7：PlannerAgent prompt 摘要，砍掉 78% 字符

**发生了什么？**
PlannerAgent 是整个流程最慢的节点——它要让 LLM 输出一份完整的 3 天行程。老版本的 prompt 有 **23,371 个字符**，任务跑完要 6 分多钟。

**为什么会这样？**
每个 POI（景点/餐厅）都把 `description`（长描述）、`photos`（图片 URL 列表）、`tags`（标签列表）等等全塞进 prompt。LLM 看到这么长的 prompt 就"读不过来"，注意力分散，改得也不准。

**怎么修好的？**
新增 [`_summarize_poi_for_prompt()`](file:///d:/agent1/backend/app/agents/nodes.py#L246-L299) 函数，对每个 POI 只保留四要素：`name / address / price / rating`，其他字段统统砍掉。
**prompt 长度从 23,371 字符降到 4,963 字符（减少 78%）**。

**效果**：
- 任务耗时从 6 分 42 秒 → 约 4 分钟
- LLM 看得更清楚，遵循用户意见的准确度也提升
- 后续还能进一步精简（比如只取 `name/address/rating`，效果可能更好）

#### 修复 6：连续提多条意见被"行程正在修订中"挡住

**发生了什么？**
用户提第 1 条意见后想再提第 2 条意见，前端弹窗提示"行程正在修订中，请等待"。可是用户明明没点"重新生成"按钮啊，为什么就"在修订中"了？

**为什么会这样？**
老版本的设计是"提一条意见就立刻触发一次 patch_plan 后台任务"，所以第 1 条意见一提交，后端立刻把 `plan.status` 改成 `revising`（修订中）。第 2 条意见提交时，后端检查状态发现 `revising` 就拒绝了。

这种设计有两个问题：
1. **小改动也要重跑整条 AI 链路**，消耗大
2. **用户提意见被卡住**，体验差

**怎么修好的？**
重新设计工作流：
- `submit_feedback` / `edit_feedback` 只把意见写到数据库，**不再启动后台任务**
- 任务的触发**统一收口到"重新生成行程"按钮**，由用户主动点
- 错误文案同步更新："行程正在修订中，请等待当前任务完成后再提交反馈" → 更准确描述实际情况

**效果**：用户可以连续提 5、6 条意见都没问题，最后点一个按钮让 AI 一次性处理。

#### 修复 3：同一 plan_id 并发跑多个 revision 任务

**发生了什么？**
用户反馈一条意见后**还没等任务跑完**，就又点"重新生成"按钮。结果两个 revision 任务同时跑，两个都跑完后写库冲突，状态被覆盖成 `failed`。

**为什么会这样？**
`submit_feedback` / `regenerate_plan` / `edit_feedback` 三个接口都没有并发控制。`asyncio.create_task` 是"创建了就跑"，不管前面那个跑没跑完。

**怎么修好的？**
在 [trip.py](file:///d:/agent1/backend/app/api/routes/trip.py#L46-L65) 加两样东西：

2. **`_revision_running`** 字典：标记当前 plan_id 是不是在跑

在三个接口层都做检查：如果在跑，直接返回 400 + "行程正在修订中，请等待完成"。
后台任务跑完（成功、失败、异常都算）都在 `finally` 里清理标记、释放锁。

**效果**：并发点击只会有一个任务真正跑，其他都被友好拒绝。


### 棘手问题 1：点完"重新生成行程"按钮，看不出变化

**用户看到的现象**：
用户提了 1~2 条意见（比如"午餐换成中餐"、"想去水族馆"），点完"根据所有反馈重新生成行程"按钮，等了 4~6 分钟，行程**看起来跟之前差不多**，于是怀疑"没生效"。

**实际发生了什么**（我们查了日志和数据库）：
regenerate **实际上是有效的**——数据库里 v2 跟 v1 是不一样的，景点换了、餐厅换了。但有 3 个原因让用户感觉"没变"：

#### 原因 A：任务跑太久，用户没耐心等完
PlannerAgent 节点调用百炼 API 让 LLM 生成新行程，**最长要 6~7 分钟**（老版本 prompt 有 23,371 字符）。用户在进度页等 30 秒没动静就关掉了，没等到 v2 落库。

**证据**：日志里 `planner_agent_node prompt 构造完成，长度=23371` 出现 6 分钟后才有下一行 `LLM 调用完成`。

#### 原因 B：LLM 改得不完全
用户说"午餐换成中餐"，LLM 确实把午餐改了，但**晚餐（西餐厅）还保留**——LLM 不是逐条精准执行，而是大致理解用户意图后自由发挥。

**证据**：v3→v4 对比，午餐从"喜苑餐厅(西餐)"变成"唐苑(开发区店)(中餐)" ✓，但晚餐还是"相聚小镇西餐融合菜餐厅" ✗。

#### 原因 C：必去景点靠"后处理补丁"补上
PlannerAgent 输出后，系统代码会检查用户提的必去景点（比如"水族馆"）有没有出现在结果里，**没出现就强制插回去**。这导致 v2 看起来"格式更乱"。

**证据**：日志里 `planner_agent_node 发现缺失的必去景点: ['水族馆']` → `将必去景点 水族馆 插入到第 2 天`。

#### 实际的 v3 → v4 对比
```
第1天 v3: 湖光岩风景名胜区              v4: 动物园-海洋馆、企鹅馆    ← 意见1生效
第2天 v3: 赤坎老街/赤坎民国风情街/      v4: 湛江华侨城欢乐海湾、     ← 意见1落实（系统后处理补的）
         寸金桥公园/寸金动物园                  水族馆
第2天 v3 午餐: 喜苑餐厅 (西餐)         v4 午餐: 唐苑(开发区店) (中餐)  ← 意见2部分生效
第2天 v3 晚餐: 相聚小镇西餐             v4 晚餐: 相聚小镇西餐            ← 意见2没改
```

**根因总结**：
1. PlannerAgent prompt **太长**（23K 字符），LLM 注意力分散，没完全遵循要求
2. 后处理代码**只能补景点、补不了"用户希望删除/替换的餐厅"**
3. 前端**看不到 diff 摘要**（用户只能看 SSE 节点名，看不到 LLM 实际改了什么）

**已规划改进**：

| 改进项 | 涉及文件 | 目的 |
|---|---|---|
| PlannerAgent prompt 摘要机制（每个 POI 只取 name/address/rating） | [nodes.py](file:///d:/agent1/backend/app/agents/nodes.py#L246-L299) | 降低 LLM 注意力分散 |
| finalize_node 写 "v3 → v4 实际修改 diff" 到数据库 | [nodes.py](file:///d:/agent1/backend/app/agents/nodes.py#L1796-L1879) | 任务完成后能回看真实改动 |
| 前端 Result.vue 加"本次重新生成修改了 N 处"提示 | [Result.vue](file:///d:/agent1/frontend/src/views/Result.vue) | 用户一眼看到"确实生效了" |
| 反馈抽取时标记 `action.type="replace_meal"` + `target_name="相聚小镇西餐..."` | [nodes.py](file:///d:/agent1/backend/app/agents/nodes.py) | Planner 知道要替换的具体对象 |

### 版本 1.8：城市攻略 RAG 增强

**要解决什么问题**

当前 RAGAgent 只从 Qdrant 向量库检索"已经导入的城市攻略文档"。如果向量库为空，RAGAgent 直接返回空字符串，PlannerAgent 缺少对城市整体游玩风格的参考，生成的整体建议比较泛。

而景点背景知识（AttractionAgent 路径）已经有"先查缓存，未命中则调百度百科，结果写回缓存"的机制。城市攻略和景点背景不同：
- 景点背景是针对**单个实体**的客观介绍，百度百科质量尚可，抓一次就能复用；
- 城市攻略是针对**整个城市**的游玩建议，更泛、更主观，百度百科往往给不出"3 天怎么玩""本地人推荐路线"这类系统性内容。

**改进目标**

给 PlannerAgent 提供**整体城市游玩建议**，而不是零散景点介绍。这类内容更适合通过爬虫批量收集优质攻略文档（如马蜂窝、小红书、穷游等平台的城市游记/攻略），经过清洗、分块、Embedding 后导入 Qdrant，再由 RAGAgent 按 `"{city}旅游攻略" + 偏好标签` 检索使用。

**预期做法**

1. **新增城市攻略爬虫/导入工具**
   - 针对目标城市批量抓取优质攻略页面。
   - 对 HTML 做清洗，提取正文，去掉广告、导航、评论区等噪声。
   - 按段落或主题分块（如"Day 1 推荐""美食街区""交通提示"）。

2. **批量写入 Qdrant**
   - 用 Embedding 模型把攻略块编码成向量。
   - 写入时带上 `city`、`source_type="city_guide"`、`url`、`title` 等元数据，方便 RAGAgent 按城市过滤。

3. **RAGAgent 增强**
   - 保持现有检索逻辑，但要求向量库中必须有城市攻略数据。
   - 检索失败时返回空字符串，仍不影响主流程。

4. **PlannerAgent Prompt 调整**
   - 当 `rag_context` 非空时，明确要求参考城市攻略中的整体建议。
   - 例如：优先按攻略推荐的区域/主题安排每日行程，而不是仅按距离最近安排。

**与景点背景知识的区别**

| 维度 | 景点背景知识（AttractionAgent） | 城市攻略（RAGAgent） |
|---|---|---|
| 目标 | 让单个景点的描述更真实 | 让整体行程更有城市特色 |
| 数据源 | 百度百科 | 马蜂窝/小红书/穷游等攻略 |
| 数据形态 | 单个词条摘要 | 多篇攻略文档分块 |
| 更新方式 | 首次搜索时自动抓取并缓存 | 需要批量爬虫或人工导入 |
| 使用时机 | AttractionAgent 拿到景点列表后 | PlannerAgent 生成行程前 |

**预期效果**

- PlannerAgent 生成的 `overall_suggestions` 更具体，能提到"本地人常去的老城区""适合傍晚去的海湾"等信息。
- 每日主题不再只是"第 X 天行程"，而是"老街文化游""滨海休闲日"等。
- 同一城市多次规划时，攻略知识可复用，越用越准。

- `backend/app/services/crawler_service.py`（新增）：城市攻略爬虫与清洗
- `backend/app/services/rag_service.py`（修改）：增加批量导入攻略文档方法
- `backend/app/agents/nodes.py`（修改）：RAGAgent 检索逻辑可保持，但 Prompt 中强化使用
- `backend/app/agents/prompts.py`（修改）：PlannerAgent Prompt 增加对攻略上下文的利用
