## 系统概览

### 1. 核心理念：流水线式多 Agent + 反馈驱动迭代

把项目想成一家"AI 旅行社"，有三件事最关键：

1. **流水线式协作**——把"理解需求 → 查景点 → 查酒店 → 算路线 → 生成行程 → 算账"拆给不同的"AI 员工"（Agent）做，每个员工只做一件事，但做得精。
2. **数据双驱动**——实时数据（高德 POI、天气）告诉你"有什么"，知识库（百度百科 + 向量库）告诉你"它是什么"。LLM 拿到这两类信息再写行程，比"凭空写"靠谱得多。
3. **反馈驱动迭代**——行程不是一次性的，用户可以提意见，AI 重新做。每次都留版本，**用户能对比"这次比上次改了什么"**。

> **为什么是"流水线"而不是"一个大 AI 写全部"？** 单一 LLM 同时处理"理解需求 + 检索 100 个景点 + 算 50 段路线 + 排每天时间 + 写自然语言描述"很容易丢三落四。让"专人做专事"，每步都能聚焦，错误率显著下降。

> **为什么允许"重新生成"？** 真实用户第一次拿到的行程往往要改——餐厅不喜欢、想换景点、要加酒店。**让 AI 学会"按用户反馈改"才是真正的智能**，而不是一次性的输出。

```
用户提交旅行需求
    │
    ▼
  意图理解  ──→  [intent_agent] 解析"去哪、几天、必去景点、预算"
    │
    ▼
  并行查信息  ──→  [attraction / weather / hotel / food / rag] 五路并发查
    │                   │ 高德 POI   │ 高德天气   │ 高德酒店   │ 高德餐饮   │ 百度百科+向量库
    ▼
  算路线   ──→  [route_agent] 算景点间距离时间（24×23=552 次路径 API，asyncio.gather 并行）
    │
    ▼
  生成行程  ──→  [planner_agent] LLM 综合生成多日 TripPlan
    │
    ▼
  算账    ──→  [budget_agent] 门票/餐饮/酒店/交通分项预算
    │
    ▼
  持久化   ──→  [finalize_node] 写数据库 + 算 diff_summary + SSE 推 completed
    │
    ▼
  展示给用户 ──→  [前端 Result.vue] 卡片化展示 + 每日反馈抽屉 + 重新生成按钮
    │
    ▼
  用户提反馈（可多条）  ──→  [只入库，不立刻启动]
    │
    ▼
  用户点"重新生成行程"  ──→  同样的 11 节点流水线再跑一次
    │
    ▼
  v2 + 蓝色 diff 高亮  ──→  用户看到"这次改了 N 处"
```

```
        │                                │                                   │
        │  - city                        │  - intent_analysis                │  - day_plans[]
        │  - dates                       │  - attractions[]                  │  - weather[]
        │  - must_visit                  │  - hotels[]                       │  - budget
        │  - preferences[]               │  - weather[]                      │  - overall_suggestions
        │  - free_text_input             │  - route_matrix{}                 │
        │                                │  - rag_context                    │
        │                                │  - final_plan                     │

        │                                │  - error                          │
        │                                │                                   │
        ▼                                ▼                                   ▼
  Pydantic 校验  ──→  顺序执行 11 节点  ──→  Pydantic 序列化

```

#### 阶段 1：解析用户表单

```
用户表单字段                    Pydantic 校验                      数据库
    │                              │                                │
    ▼                              ▼                                ▼
Home.vue ─POST /api/trip/plan─> trip/plans.py ──Pydantic──> trip_plans 表 (pending)
       (JWT)              │  校验 城市/日期/天数            │
                          │                                 │
                          ▼                                 │
                     JWT 鉴权 ──> 无 Token → 401             │
                          │                                 │
                          ▼                                 │
                     asyncio.create_task 启动后台 ──────────> plan_revisions 表 (v1, source=initial)
```

**关键点**：

- **Pydantic 校验在请求边界做**——字段类型不对、缺必填项，400 直接返回，不消耗 LLM token
- **JWT 鉴权**——所有业务接口都要 `Authorization: Bearer <token>`，否则 401
- **asyncio.create_task 启动后台**——POST 不等任务完成，立刻返回 `plan_id`，让前端去开 SSE 监听

#### 阶段 2：11 节点流水线

```
trip_plans (pending)                             
    │                                            
    ▼                                            
graph.py: run_planning_graph()                  
    │                                            
    │  11 个节点顺序 await：                      
    │                                            
    │  1. intent_agent_node      ──→ 解析为 IntentAnalysis
    │  2. attraction_agent_node  ──→ 高德 POI + RAG 补背景
    │  3. weather_agent_node     ──→ 高德天气
    │  4. hotel_agent_node       ──→ 高德酒店
    │  5. food_agent_node        ──→ 高德餐饮
    │  6. rag_agent_node         ──→ 城市攻略 RAG
    │  7. route_agent_node       ──→ asyncio.gather 并行算路线
    │  8. planner_agent_node     ──→ LLM 生成 TripPlan
    │  9. budget_agent_node      ──→ 分项预算
    │  10. human_in_the_loop     ──→ 预算超支暂停审批
    │  11. finalize_node         ──→ 写库 + 算 diff + SSE completed
    │                                            
    ▼                                            
trip_plans (completed) + plan_revisions (v1, is_current=1) + SSE type=completed
```

**为什么是 11 个节点而不是 1 个超级 Agent？**

| 维度 | 单 Agent 一把梭 | 11 节点流水线（当前） |
|------|----------------|---------------------|
| 错误率 | 高（所有事一起做容易丢） | 低（每步只做一件事） |
| 可调试性 | 差（一步错全错） | 好（错在哪步立刻知道） |
| 灵活性 | 改 1 处动全身 | 改 1 个节点即可 |
| 速度 | 不一定快（token 用得多） | 并行部分快 |
| 面试价值 | 一般 | 强（体现多 Agent 架构） |

## 4. 11 个 Agent 节点详细说明

> 本节按流水线顺序逐个讲清楚每个 Agent 是干什么的、输入什么、输出什么、什么时候会出错。

### 4.1 IntentAgent（意图理解）

```
输入：TripRequest (原始表单)
  ├─ city: "湛江"
  ├─ start_date: "2026-08-01"
  ├─ travel_days: 3
  ├─ preferences: ["海鲜", "文化"]
  ├─ must_visit: ["赤坎老街"]
  └─ free_text_input: "想多看历史，不要太累"

   │
   │ LLM 解析 + Prompt 模板
   ▼

输出：IntentAnalysis
  ├─ city: "湛江"
  ├─ travel_days: 3
  ├─ preferences: ["海鲜", "文化", "历史", "轻松"]
  ├─ must_visit: ["赤坎老街"]
  ├─ budget_level: "standard"
  ├─ pace: "relaxed"          ← LLM 从"不要太累"推断
  └─ notes: "用户希望行程节奏宽松，侧重历史文化与海鲜美食"
```

**为什么需要这个节点？** 用户填的是"自然语言 + 几个标签"，需要 LLM 把它翻译成后续 Agent 能直接用的结构化数据。

**典型问题**：

- 用户的"不要太累" → 推断为 `pace="relaxed"` → PlannerAgent 自动少排景点
- 用户的"必去赤坎老街" → 写入 `must_visit: ["赤坎老街"]` → AttractionAgent 强制保留

### 4.2 AttractionAgent（景点检索）

```
输入：IntentAnalysis
  ├─ city: "湛江"
  ├─ must_visit: ["赤坎老街"]
  └─ preferences: ["海鲜", "文化", "历史"]

   │
   │ 1. 高德 POI 搜索（按偏好分多轮）
   │    ├─ 关键词 "历史文化景点" → 返回 10 个
   │    ├─ 关键词 "海鲜美食街"   → 返回 8 个
   │    └─ 关键词 "休闲公园"     → 返回 5 个
   │    去重、过滤无坐标、按评分排序 → ≤ 10 个
   │
   │ 2. RAG 补背景（asyncio.gather 并行）
   │    batch_search_or_fetch(["赤坎老街", "金沙湾", ...], city="湛江")
   │    ├─ 命中缓存 → 直接返回
   │    └─ 未命中 → 爬百度百科 → 入向量库
   │
   ▼

输出：List[Attraction]（每个景点含完整 POI 信息 + RAG 背景）
  ├─ id: "B001000ABCD"
  ├─ name: "赤坎老街"
  ├─ location: {longitude: 110.36, latitude: 21.27}
  ├─ description: "湛江现存最完整的骑楼建筑群..."  ← RAG 补的
  ├─ image_url: "https://..."
  ├─ rating: 4.6
  ├─ ticket_price: 0
  └─ detail_url: "https://ditu.amap.com/..."
```

**关键设计**：

- **景点数 ≤ 10**——多了 LLM 处理不完，也容易超 prompt token 限制
- **RAG 补背景放在这一步**——而不是 PlannerAgent 阶段，让每个景点自带丰富描述，PlannerAgent 看到的就是"已经查好的信息"
- **`must_visit` 强制保留**——代码层校验 AttractionAgent 返回列表里必须包含用户必去的景点

### 4.3-4.6 Weather / Hotel / Food / RAG 四个节点

这 4 个节点和 AttractionAgent **结构类似**，都是"调外部 API + 简单整理"。

```
┌─ weather_agent_node ─────────────────────────────┐
│  输入: 城市 + 日期范围                              │
│  工具: 高德 weather API                            │
│  输出: List[WeatherInfo] (每天一条)                │
│  容错: 高德只返回未来 4 天，超出的用历史同期补       │
└──────────────────────────────────────────────────┘

┌─ hotel_agent_node ───────────────────────────────┐
│  输入: 城市 + 住宿类型 + 景点中心坐标                │
│  工具: 高德 text_search "酒店"                     │
│  策略: 按景点中心附近 5km 搜，按距离+评分+价格排序   │
│  输出: List[Hotel] (3-5 个)                       │
└──────────────────────────────────────────────────┘

┌─ food_agent_node ─────────────────────────────────┐
│  输入: 城市 + 用餐时间 + 用户偏好                   │
│  工具: 高德 POI 搜索 + 偏好关键词                   │
│  策略: 早中晚各搜一次，按 "评分高 + 价格合理" 选 1-2 │
│  输出: List[Meal] (早中晚各 2 个候选)              │
└──────────────────────────────────────────────────┘

┌─ rag_agent_node ─────────────────────────────────┐
│  输入: 城市名 + 偏好标签                            │
│  工具: RAGService.search_or_fetch                 │
│  策略: 查本地缓存 → 未命中则爬百度百科               │
│  输出: rag_context (字符串，喂给 PlannerAgent)     │
└──────────────────────────────────────────────────┘
```

**并行关系**：

```python
# 这 4 个节点是并行执行的（在 graph.py 中是顺序写法，但实际都在一个 for 循环内）
# 实际代码里 attraction / weather / hotel / food / rag 是顺序的
# 因为都需要 IntentAnalysis 作为前置输入
# 后续 PlannerAgent 等所有节点都完成后才启动
```

### 4.7 RouteAgent（路线规划）

```
输入：List[Attraction] (≤ 10 个) + 交通方式

   │
   │ asyncio.gather 并行算 10×9 = 90 对路径
   │   │ 每对：origin=A, destination=B, mode=driving
   │   │ 高德 direction API
   │   ▼
   │ best_route = {distance, duration, polyline, steps}
   │
   ▼

输出：route_matrix (Dict[(a_id, b_id), RouteInfo])
  ├─ ("B001", "B002"): {distance: 3200m, duration: 12min, polyline: "..."}
  ├─ ("B001", "B003"): {distance: 5800m, duration: 18min, polyline: "..."}
  └─ ...
```

**为什么必须并行？**

- 10 个景点两两配对 = **90 对**（公式 `n*(n-1)`）
- 串行调用 90 次高德 API ≈ **10 分钟**（每次 ~6s）
- 并行 asyncio.gather ≈ **15-20 秒**
- 不并行的话用户会以为"系统卡死了"

> **踩坑记录**：早期没并行，路线计算 10 分钟，疑似"系统挂掉"。详见 [问题排查记录.md 问题 2](file:///d:/agent1/docs/问题排查记录.md)。

### 4.8 PlannerAgent（行程生成，最关键）

```
输入：
  ├─ IntentAnalysis (用户偏好)
  ├─ List[Attraction] (≤ 10 个候选景点 + 完整 RAG 背景)
  ├─ List[Hotel] (酒店候选)
  ├─ List[WeatherInfo] (天气)
  ├─ route_matrix (景点间距离时间)
  └─ rag_context (城市攻略)

   │
   │ 1. POI 摘要：_summarize_poi_for_prompt()
   │    把 10 个 POI 压成 5K 字符以内（-78%）
   │    完整 name + location + rating + 缩略 description
   │
   │ 2. LLM 调用百炼
   │    Prompt 模板: prompts.PLANNER_HUMAN_TEMPLATE
   │    必包含字段: must_visit 强制保留
   │    输出约束: 严格 JSON Schema
   │
   │ 3. JSON 容错解析（3 次尝试）
   │    ① 严格 Pydantic 校验
   │    ② 宽松（去掉多余字段）
   │    ③ _replace_none_with_defaults（null 兜底为默认值）
   │
   ▼

输出：TripPlan
  ├─ city: "湛江"
  ├─ start_date: "2026-08-01"
  ├─ day_plans: [
  │   DayPlan {
  │     day_index: 1,
  │     attractions: [Attraction, Attraction, Attraction],
  │     meals: {breakfast: Meal, lunch: Meal, dinner: Meal},
  │     hotel: Hotel,
  │     transport: "自驾",
  │     weather: WeatherInfo
  │   },
  │   ...
  │ ]
  ├─ budget: {transport: 0, hotel: 1200, meal: 800, ticket: 200, total: 2200}
  └─ overall_suggestions: "湛江 8 月天气炎热，建议多喝水..."
```

**为什么 PlannerAgent 是"最关键"？**

| 原因 | 说明 |
|------|------|
| **输出结构最复杂** | 嵌套 4 层（TripPlan → DayPlan → Attraction/Meal/Hotel → Location） |
| **必须用 LLM** | 其他节点都是查数据，只有它需要"写"——综合偏好、景点、距离、天气生成行程 |
| **最容易出错** | LLM 输出格式不规整 → Pydantic 校验失败 → 整次任务失败 |
| **最耗 token** | 单次 prompt 23K 字符（已优化到 5K），response 几 K 字符 |
| **决定行程质量** | 前面 7 个节点都只是"准备食材"，这一节点是"做菜" |

**踩坑记录**：

- **Prompt 太长（23K 字符）**——LLM 注意力分散，漏改某些意见。修复：`_summarize_poi_for_prompt()` 把 POI 摘要到 5K 字符以内。
- **Pydantic 校验 42 个错误**——LLM 把 float 字段输出为 `null`。修复：`Optional[float]` + `_replace_none_with_defaults()`。

### 4.9 BudgetAgent（预算核算）

```
输入：TripPlan (含 attractions/hotels/meals)

   │
   │ 按公式统计:
   │   门票 = Σ attraction.ticket_price
   │   餐饮 = Σ meal.estimated_cost (3 天 × 3 餐)
   │   酒店 = hotel.price_per_night × (travel_days - 1)
   │   交通 = Σ route_info.tolls (自驾模式) 或 0
   │   合计 = 四项之和
   │
   ▼

输出：Budget (填到 TripPlan.budget)
  ├─ transport: 0
  ├─ hotel: 1200
  ├─ meal: 800
  ├─ ticket: 200
  └─ total: 2200
```

**注意**：这里**不调 LLM**，纯代码计算。LLM 在 PlannerAgent 阶段已经填了部分字段，这里是**校验 + 补全**。

### 4.10 HumanInTheLoop（人机协同）

```
当前实现（M3 真 HITL）：
  - BudgetAgent 判定预算超支 → 节点不再自动放行：写 checkpoint、
    任务置为 pending_approval、SSE 推审批事件，任务正常返回暂停
  - 用户经 POST /api/trip/{plan_id}/approve 审批通过后，
    从断点 checkpoint 续跑剩余节点
  - 未超支 → 直接通过
```

### 4.11 FinalizeNode（收尾）

```
输入：完整 TravelPlanningState（含 TripPlan）

   │
   │ 1. 算 diff_summary（与上一版对比）
   │    如果是 v1，diff_summary = null
   │    如果是 v2+，diff_summary = {
   │      "added_attractions": [...],
   │      "removed_attractions": [...],
   │      "changed_meals": [...],
   │      "changed_hotel": [...]
   │    }
   │
   │ 2. 写数据库
   │    UPDATE trip_plans SET plan_data=?, status='completed'
   │    INSERT INTO plan_revisions (version, trip_plan_json, diff_summary, is_current=1)
   │    UPDATE plan_revisions SET is_current=0 WHERE plan_id=? AND id != current
   │
   │ 3. SSE 推送 type=completed
   │
   ▼

输出：状态变更
  ├─ trip_plans.status = "completed"
  ├─ plan_revisions 新增一行 (v1 or v2 or v3)
  ├─ 旧版本 is_current = 0
  └─ SSE 客户端收到 type=completed 事件
```

**为什么"finalize 才写库"？**

- 前面 10 个节点**任何一步失败都不污染数据库**
- 数据库始终是"完整的、最新的、可用的"状态
- 用户看到 `failed` 时，数据库没有半成品

## 5. 反馈与重新生成：项目的灵魂

> 如果只能讲一个功能，**讲反馈与重新生成**。这是项目最有特色的部分，也是面试时的最大亮点。

### 5.1 为什么需要"重新生成"？

| 场景 | 用户的真实体验 |
|------|---------------|
| 第一次拿到的餐厅是西餐 | "我不喜欢西餐，能不能换中餐？" |
| 行程太赶 | "3 天安排 12 个景点太累了，少排点" |
| 酒店位置偏 | "酒店离景点太远了，换市中心的" |
| 想加必去景点 | "我没看到我必去的 XX，能不能加上" |

**没有重新生成**：用户只能从头提需求，重新跑一遍（也记不住上次到哪了）

**有重新生成**：用户提 N 条意见 → 点按钮 → 系统按意见重做，**还保留历史版本**

### 5.3 关键设计决策

| 决策 | 为什么 | 反例（如果不做） |
|------|--------|-----------------|
| **单条意见只入库，不立即启动任务** | 用户可能还要继续提意见 | 提 1 条就消耗 1 次 LLM，提 5 条就跑 5 次 |
| **统一收口到"重新生成"按钮** | 用户能"提完一起处理" | 改一半就触发，状态机混乱 |
| **`complexity="full"` 强制整体重排** | partial patch 容易改坏其他天 | 单天改对，其他天变样 |
| **per-plan 互斥锁** | 防止并发写库冲突 | 同时点 2 次"重新生成" → 数据库冲突 → 状态变 `failed` |
| **`is_current` 字段管理版本** | 前端查 `is_current=1` 永远拿到最新 | 需要按时间排序，逻辑复杂 |
| **`diff_summary` 字段** | 没有它用户感知不到变化 | "重新生成没生效！" |
| **`window.location.href` 整页刷新** | `router.push` 不会触发 onMounted | 数据不刷新，旧版还显示 |
| **`is_withdrawn` 软删除** | 撤回后历史可追溯 | 硬删 → 反馈历史消失 |

### 6.2 三张核心表详解

#### 表 1：trip_plans（行程主表）

**这是"行程的入口"，每个 plan_id 唯一对应一次"提交需求 + 生成行程"的尝试。**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String PK | `"PLAN_xxxxxxxx"` |
| `user_id` | FK | 所属用户 |
| `city` | String | 目的地城市 |
| `start_date` | String | 出发日期 |
| `end_date` | String | 结束日期 |
| `travel_days` | Integer | 天数 |
| `plan_data` | JSON | **当前生效版本**的完整 TripPlan（默认就是最新版） |
| `status` | String | `pending` / `running` / `completed` / `failed` / `revising` |
| `created_at` | DateTime | 创建时间 |
| `updated_at` | DateTime | 最后修改时间 |

**状态机**：

```
pending ──→ running ──→ completed
                │
                ├─→ failed（任意节点异常）
                │
                └─→ revising ──→ running ──→ completed
                       (重新生成)        (v2)
```

#### 表 2：plan_revisions（版本历史表）★ 项目核心

**这是"重新生成"功能的数据基础。每次生成都新建一行，旧版 `is_current=0`。**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | Integer PK | 自增 |
| `plan_id` | FK | 关联 trip_plans |
| `version` | Integer | `1`, `2`, `3`... |
| `source` | String | `initial` (首次) / `full` (整体重排) / `patch` (局部) |
| `trip_plan_json` | JSON | **该版本的完整 TripPlan 快照** |
| `diff_summary` | JSON | **与上一版的差异**（v1 为 null） |
| `feedback_ids` | JSON | 触发生成此版本的 feedback id 列表 |
| `is_current` | Boolean | `True` = 当前生效版本 |
| `created_at` | DateTime | 创建时间 |

**关键示例**：

```
plan_id = "PLAN_xxx"

plan_revisions 表:
┌────┬─────────┬─────────┬────────┬──────────────────┬──────────┐
│ id │ version │ source  │diff_sum│ is_current       │ created  │
├────┼─────────┼─────────┼────────┼──────────────────┼──────────┤
│ 1  │ 1       │ initial │ null   │ 0 ← v2 之后变 0  │ 7-15 10:00│
│ 2  │ 2       │ full    │{3 处}  │ 1 ← 当前版本      │ 7-15 10:30│
└────┴─────────┴─────────┴────────┴──────────────────┴──────────┘
```

#### 表 3：plan_feedbacks（用户反馈表）

**这是"重新生成"的输入数据。每条反馈都入库，等用户点"重新生成"按钮才聚合使用。**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | Integer PK | 自增 |
| `plan_id` | FK | 关联 trip_plans |
| `revision_id` | FK | 关联 plan_revisions（针对哪个版本提的） |
| `user_id` | FK | 哪个用户提的 |
| `day_index` | Integer | 第几天的反馈（`NULL` = 整体反馈） |
| `raw_text` | Text | 用户原始意见 |
| `tags` | JSON | 快选标签 |
| `structured_feedback` | JSON | LLM 抽取的结构化反馈（可选） |
| `is_withdrawn` | Boolean | 软删除标记 |
| `created_at` | DateTime | 提交时间 |

**关键示例**：

```
plan_id = "PLAN_xxx"

plan_feedbacks 表:
┌────┬──────────────┬─────────┬──────────────────────────────────────────┐
│ id │ day_index    │withdrawn│ raw_text                                 │
├────┼──────────────┼─────────┼──────────────────────────────────────────┤
│ 1  │ 2            │ 0       │ 中餐不要西餐，酒店要更近些                  │
│ 2  │ 3            │ 0       │ 早餐换一茶一点 → 榕意                      │
│ 3  │ 2            │ 1       │ 算了，第 2 天不改了  ← 软删除，不影响聚合    │
└────┴──────────────┴─────────┴──────────────────────────────────────────┘

聚合 SQL：
SELECT * FROM plan_feedbacks 
WHERE plan_id = ? AND is_withdrawn = 0 
ORDER BY day_index, id

聚合结果：
"第 2 天: 中餐不要西餐，酒店要更近些\n
 第 3 天: 早餐换一茶一点 → 榕意"
```

### 6.3 三张表的关系速记

```
User 1 ──── N TripPlan
TripPlan 1 ─ N PlanRevision  (一个行程多版本，is_current=1 才是当前)
TripPlan 1 ─ N PlanFeedback  (一个行程多条反馈，is_withdrawn=0 才有效)
PlanRevision 1 ─ N PlanFeedback  (每条反馈可能引用某个版本)

User 1 ── 1 UserPreference  (每个用户一套结构化偏好)
User 1 ── N UserMemory  (每个用户多条事件级记忆)
```

### 7.1 RAG 在项目里的位置

```
11 节点流水线里，RAG 只在 2 个地方被调用：
                                                      
1. AttractionAgent (节点 2)                               
   ├─ 拿到候选景点后                                     
   ├─ 调 RAG 给每个景点补背景（asyncio.gather 并行）       
   └─ 把背景塞到 attraction.description                   
                                                      
2. RAGAgent (节点 6)                                    
   ├─ 拿到城市名 + 偏好                                  
   ├─ 调 RAG 查城市攻略                                  
   └─ 输出 rag_context 字符串，喂给 PlannerAgent         
                                                      
其他节点都不用 RAG。                                    
```

### 7.2 搜索优先 + 渐进积累（核心设计）

```
用户搜索 "湛江 赤坎老街"
    │
    ▼
┌─ Step 1: 查本地缓存 (Qdrant 或内存字典) ────────────┐
│  query → embedding → 搜 Top-K                       │
│  ├─ 命中 (score ≥ 0.75) → 直接返回 ✅                │
│  └─ 未命中 (score < 0.75) → Step 2                  │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─ Step 2: 外部搜索 (百度百科) ───────────────────────┐
│  搜 "湛江 赤坎老街" → 解析第一条词条 → 抽摘要         │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─ Step 3: 写入缓存 (供下次用) ──────────────────────┐
│  摘要 → 切分 (chunk_size=500) → embedding → 入库    │
└─────────────────────────────────────────────────────┘
    │
    ▼
返回 {content, from_cache=False, url}

下次再搜 "赤坎老街"：
  Step 1 命中 ✅（缓存里有），from_cache=True
```

**为什么"不预先爬取大量攻略导入向量库"？**

| 方案 | 优 | 劣 |
|------|----|----|
| **预导入**（爬 100 万攻略入库） | 查询快 | 维护成本高、数据易过时、初始投入大 |
| **搜索优先 + 渐进积累**（当前方案） | 维护成本低、数据新鲜、越用越全 | 第一次慢（要爬） |

我们的取舍：MVP 阶段选**轻量**——用户查 1 次，缓存 1 次，1 周后系统就"懂"了这个城市。

### 7.3 当前局限与鲁棒性

**真实开发中遇到的 2 个坑**：

| 局限 | 现象 | 代码如何兜底 |
|------|------|--------------|
| **torch DLL 加载失败** | `Error loading ... torch\lib\c10.dll` | RAGService 启动时 try/except，失败就只走百度百科原文（不经向量编码） |
| **Qdrant 未启动** | `[WinError 10061] 连接被拒绝` | 失败就置为内存模式（重启后丢失） |

**核心原则**：**RAG 是"锦上添花"而非"雪中送炭"**——核心行程生成不依赖 RAG，RAG 只让描述更丰富。

## 8. 实时进度推送：SSE 协议

### 8.1 为什么用 SSE 不用 WebSocket？

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 方向 | 服务器 → 客户端（单向） | 双向 |
| 协议 | HTTP（兼容） | 独立协议 |
| 实现复杂度 | 低 | 中 |
| 适用场景 | 实时进度推送 | 聊天、协作编辑 |
| 本项目需要 | ✅ 单向进度 | ❌ 不需要双向 |

**SSE 完全够用**——前端只需要"接收进度"，不需要"发送消息"。

### 8.2 SSE 数据格式

```javascript
// 前端 EventSource 收到的格式
event: agent_progress
data: {"node": "intent_agent", "status": "started", "ts": 1721030400}

event: agent_progress  
data: {"node": "attraction_agent", "status": "running", "ts": 1721030401}

event: agent_progress
data: {"node": "finalize_node", "status": "completed", "ts": 1721030450}

event: done
data: {"type": "completed", "plan_id": "PLAN_xxx"}
```

### 8.3 关键代码

```python
# backend/app/api/routes/agent.py
@router.get("/agent/trip/{plan_id}/stream")
async def stream_agent_events(plan_id: str, token: str = ""):
    async def event_generator():
        # 1. 先发历史日志（断线重连也能拿到）
        for log in streaming.get_history(plan_id):
            yield f"data: {json.dumps(log, ensure_ascii=False)}\n\n"
        
        # 2. 实时订阅新日志
        async for log in streaming.subscribe(plan_id):
            yield f"data: {json.dumps(log, ensure_ascii=False)}\n\n"
            if log.get('type') in ('completed', 'failed'):
                break
    
    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

**关键设计**：

- **先发历史再推实时**——断线重连也能拿到完整过程
- **token 用 query 而非 header**——`EventSource` API 不支持自定义 header
- **完成时主动 break**——避免 SSE 连接一直挂着

### 8.4 前端跳转

```javascript
// Planning.vue
watch(() => sseEvents.value, (events) => {
  const last = events[events.length - 1]
  if (last?.type === 'completed') {
    // ★ 关键：window.location.href 而非 router.push
    // ★ 原因：router.push 不触发 onMounted，旧数据不刷新
    window.location.href = `/result/${planId}?from=regenerate&refresh=${Date.now()}`
  }
})
```

## 9. 关键设计决策的对比

> 这些决策都是项目演进中"踩坑后改的"，看历史背景有助于理解为什么现在是这样。

### 9.1 LangGraph `ainvoke` → 手动顺序 `await`

| 维度 | LangGraph ainvoke | 手动 await |
|------|------------------|-----------|
| 抽象 | StateGraph 节点+边 | 同样的 State/Node/Edge 概念 |
| 执行 | 框架调度 | for 循环 + await |
| 序列化 | Checkpointer 序列化 Pydantic 对象图 | 无序列化（直接操作内存） |
| 速度 | 卡死（实测 30+ 分钟） | 正常（4-5 分钟） |
| 可调试性 | 中（要查 Checkpointer） | 高（直接 await） |

**结论**：保留 State/Node/Edge 抽象，但**执行层手写**。

### 9.2 路线计算：串行 → `asyncio.gather` 并行

| 维度 | 串行 | 并行 |
|------|------|------|
| 90 对路径 API | 10 分钟 | 15-20 秒 |
| 用户感知 | "系统卡死了" | "挺快的" |
| 高德 API 限额 | 单线程稳定 | 高并发可能触发限流 |

**结论**：用 `asyncio.gather` 并行，加 `Semaphore(10)` 限流。

### 9.3 PlannerAgent prompt：23K → 5K 字符

| 维度 | 23K 字符（原始） | 5K 字符（摘要） |
|------|------------------|-----------------|
| LLM 注意力 | 分散、漏改 | 集中、能改 |
| 单次耗时 | 6-7 分钟 | 4-5 分钟 |
| 改意见落实率 | 60% | 90%+ |

**结论**：`_summarize_poi_for_prompt()` 摘要 POI 到 5K 字符。

### 9.4 单条意见立即触发 → 用户手动触发

| 维度 | 立即触发 | 手动触发 |
|------|----------|----------|
| 多次反馈 | 提 1 条就跑 1 次 | 提 N 条只入库，点按钮跑 1 次 |
| LLM 成本 | 高 | 低 |
| 用户体验 | 状态机混乱 | 清晰 |

**结论**：**只入库 + 统一收口到"重新生成"按钮**。

### 9.5 反馈收口 + 重新生成路径

| 维度 | 局部 patch | 整体 full |
|------|-----------|----------|
| 复杂度 | 高（只改某天，其他天保留） | 低（11 节点跑一遍） |
| 稳定性 | 容易改坏其他天 | 稳定 |
| 反馈落实 | 看 LLM 心情 | 更好 |

**结论**：**当前默认 `complexity="full"`**，patch 路径保留作未来选项。

### 9.6 Vue Router 跳转 → `window.location.href`

| 维度 | `router.push` | `window.location.href` |
|------|---------------|------------------------|
| 触发 onMounted | ❌（组件复用） | ✅（整页刷新） |
| 数据更新 | 旧数据 | 新数据 |
| 性能 | 快 | 慢一点（整页 reload） |

**结论**：**SSE 完成后用 `window.location.href` 整页刷新**，绕开 Vue Router 复用组件的坑。

## 10. 调试与排错指南

> 这一节列出"开发时遇到 XXX 问题该看哪里"。

### 10.1 问题排查表

| 现象 | 看哪里 | 怎么解决 |
|------|--------|----------|
| 重新生成后状态变 `failed` | `uvicorn.err` 日志 | 搜 `MissingGreenlet` → 加 `selectinload` |
| 状态 `completed` 但行程没变 | 后端日志搜 `diff_total` | LLM 忽略意见，调 prompt 或强制更明确的反馈 |
| SSE 没进度 | 前端 Network 找 `/api/agent/.../stream` | token 鉴权失败（SSE 用 query token） |
| 页面没自动刷新 | 前端 console | 必须用 `window.location.href` 不用 `router.push` |
| RAG 一直没用 | 后端日志搜 `Error loading torch` | torch DLL 失败是预期的，会自动回退 |
| 重新生成耗时 > 5 分钟 | 后端日志搜 `finalize_node duration` | LLM 慢/网络抖，prompt 超 5K 也会慢 |
| 报错 "行程正在修订中" | 后端 `_revision_running` 状态 | 上次任务没正常结束，重启后端 |
| Pydantic 校验失败 | 后端日志搜 `ValidationError` | 看 [问题排查记录.md 问题 6](file:///d:/agent1/docs/问题排查记录.md) |
