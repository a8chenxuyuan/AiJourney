## 2026-07-14 核心问题记录

### 问题 1：Agent 流程卡住，输出占位数据

**用户看到的现象**：
- 用户在前端填好"想去湛江 3 天"提交后，等了 5 分钟
- 返回的行程里写着"示例景点 A"、"示例城市"这种占位文字
- 真实的湛江景点（湖光岩、赤坎老街、金沙湾）一个都没有

**为什么会这样？**
项目早期用了 LangGraph 0.2.x 的 `ainvoke()` 来跑整个工作流。LangGraph 默认会**自动保存 checkpoint**（中间状态），方便断点续跑。
可是我们的工作流里塞了大量 Pydantic 对象（一个景点就是一个 Pydantic 模型），序列化时**会把整个对象图都拆开重写一遍**。当对象多、状态复杂时，序列化会卡住甚至直接抛异常。

**怎么修好的？**
放弃 LangGraph 的 `ainvoke()`，**改用手动顺序调用节点**：
- 每个 Agent 节点（intent_agent、attraction_agent、...、finalize）的代码**保持不变**
- 只替换编排层，按顺序 `await` 调用每个节点，手动合并状态
- 不用 checkpoint，绕开序列化坑

**修改文件**：
- `backend/app/agents/graph.py` 第 201-319 行
- `backend/app/agents/prompts.py` 第 76-109 行

**踩过的二级坑**：
在改 `PLANNER_SYSTEM_PROMPT` 时，Python 的 `str.format()` 会把 JSON 示例中的 `{city}` 当成占位符解析，**疯狂报 `KeyError`**。解决方式是把 JSON 示例里的 `{` 转义成 `{{`、`}` 转义成 `}}`——这是 Python 字符串格式化的老规矩了。

### 问题 2：路线规划节点耗时超过 10 分钟

**用户看到的现象**：
- 后端日志里 `route_agent_node` 这一行停留很久
- 测试脚本卡在"计算景点到景点距离"那一步
- 用户在进度页看动画能看 10 分钟

**为什么会这样？**
`attraction_agent_node` 会返回最多 24 个候选景点（高德 POI），交给 `route_agent_node` 算"景点 A 到景点 B 的距离"。
老代码是**双重 for 循环串行调用高德路线 API**：24 个景点两两配对就是 `24 × 23 = 552` 次 API 调用。一次 5~10 秒，总耗时 `552 × 7.5 = 4140 秒 ≈ 69 分钟`。

**怎么修好的？**
两步：
1. 在 `attraction_agent_node` 限制景点数量上限为 **10 个**（大多数情况用不了 10 个）
2. 在 `route_agent_node` 用 `asyncio.gather` **并行调用**高德 API，10 个景点最多 `10 × 9 = 90` 次，并行后实际耗时 < 1 分钟

**修改文件**：
- `backend/app/agents/nodes.py` 第 392-471 行（景点数量限制）
- `backend/app/agents/nodes.py` 第 832-895 行（并行路线计算）

### 问题 3：前端显示示例数据，后端实际已生成真实行程

**用户看到的现象**：
- 后端日志：任务跑成功，`status=completed`，`plan_data` 字段里有"湖光岩"、"赤坎老街"等真实数据
- 前端：依然显示"示例城市"、"示例景点 A"
- 用户：❓❓❓

**为什么会这样？**
原来 `/api/agent/trip/{plan_id}/stream`（SSE 接口）是**模拟实现**——固定每 0.5 秒发一个步骤，4.5 秒就发 `completed`。
但真实的 Agent 跑完要 2~3 分钟。
前端在收到 `completed` 后**立即跳到结果页**，那时数据库里 `plan=null`（还在跑），Result.vue 拿到空 plan 就显示示例数据了。

**怎么修好的？**
3 个动作：
1. 新建 `backend/app/agents/streaming.py`：维护每个 `plan_id` 的实时日志队列和历史记录
2. 改 `backend/app/agents/graph.py`：节点执行时把日志推到 SSE 队列，完成/失败时发结束标记
3. 改 `backend/app/api/routes/agent.py`：SSE 接口从真实队列读日志，pending 时等待并发心跳，completed/failed 时结束

**修改文件**：
- `backend/app/agents/streaming.py`（新增）
- `backend/app/agents/graph.py` 第 47-52、283-314、324-326 行
- `backend/app/api/routes/agent.py` 第 28-31、147-197 行

### 问题 4：LLM 输出字段类型不匹配，规划失败

**用户看到的现象**：
- 前端 Planning.vue 能真实显示 Agent 进度
- 跑到 `planner_agent` 节点后，进度条停住，最后显示 `failed`
- 后端日志：`planner_agent_node LLM 输出解析失败`

**为什么会这样？**
LLM 输出了一段 JSON，但有几个字段类型不对：
```json
"meals": [
  {"name": "牛肉面", "estimated_cost": "20元"},  ← 字符串
  {"name": "海鲜锅", "estimated_cost": "60元"}   ← 字符串
]
```
Pydantic 模型定义 `estimated_cost: float`，**字符串不接受**，校验失败。
更糟的是，`parse_llm_json` 返回 `None` 后，下一行代码 `plan.plan_id = ...` 因为 `plan is None` 报 `AttributeError`，错误信息被覆盖了。

**怎么修好的？**
1. 给 `Meal.estimated_cost` 加 `field_validator`，**自动从字符串里提取数字**（"20元" → 20.0）
2. `parse_llm_json` 返回 `None` 时**立即抛明确异常**（"LLM 输出解析失败"），不再让 `AttributeError` 误导排障

**验证结果**：
2026-07-14 13:02 创建新行程 `PLAN_99EA873E04BB45CF`：
- 状态：`completed`
- 城市：湛江
- 3 天真实行程（湖光岩、赤坎老街、金沙湾）
- 前端正常显示真实数据 ✓

**修改文件**：
- `backend/app/models/schemas.py` 第 148-164 行
- `backend/app/agents/nodes.py` 第 996-998 行

## 2026-07-15 核心问题记录

### 问题 5：SSE 跳回 /result/{id} 时前端不刷新

**用户看到的现象**：
- 点完"根据所有反馈重新生成行程"按钮，等 4~6 分钟
- 任务跑完后，自动跳到结果页
- 页面**还是显示老的 v1 内容**——v2 明明在数据库里
- 蓝色"本次修改了 N 处"高亮框也没出现
- 手动刷新浏览器后才看到 v2

**为什么会这样？**
Vue Router 在跳转时有个特性：**如果跳转前后是同一个组件（都是 Result.vue），会复用这个组件实例，不重新触发 `onMounted` 钩子**。
我在 Result.vue 加了 `watch(() => route.params.id)` 想监测路由变化，但组件被复用后，watch 也不一定触发。
根本原因是用户经常在任务跑完前就回到 Result.vue（那时 v2 还没落库），后续即使任务跑完 v2 落库了，前端也**一直显示早先的 v1 状态**。

**怎么修好的？**
3 个动作：
1. 把 `router.push` 改成 `window.location.href = '/result/{id}?refresh=' + Date.now()`——**强制整页刷新**，绕开 Vue Router 复用组件的坑
2. 在 Result.vue 加 `manualRefresh()` 手动刷新按钮 + `showDiffSummary` 开关作为兜底
3. 后端 `GET /api/trip/{id}` 加 print 日志记录 `returning version=N, diff_total=M`，便于排障

**验证结果**：
PLAN_A9240DB453F74419：v1→v2 跑了 1 处变化（Day 3 酒店从"西江月酒店"换到"二祥宾馆(湛江医科大学附属医院店)"）。
用户提了"不想三天都住一个酒店"，v2 完美落实。
API 返回 `version=2, diff_total=1`，前端展示"本次重新生成修改了 1 处" ✓

**修改文件**：
- `frontend/src/views/Planning.vue` 第 57-62 行
- `frontend/src/views/Result.vue` 第 346-369、383-393、421-447 行
- `backend/app/api/routes/trip.py` 第 207-208 行（debug print）

### 问题 6：Pydantic float_type 验证失败导致 v2 创建失败

**用户看到的现象**：
- regenerate 跑到 planner_agent 节点时，日志连续刷 42 条错误：
  ```
  Input should be a valid number, input_value=None, input_type=NoneType
  ```
- 重试后**第二次成功**（LLM 偶尔会重写字段），但有时还是失败 → 回退到 `_build_fallback_plan`，跟 v1 一样

**为什么会这样？**
- `Budget` 模型里 `attractions / meals / hotels / transportation / total` 等字段都是 `float = Field(default=0.0)`
- Pydantic v2 严格模式**不接受 None**——你声明是 `float`，LLM 输出 `null` 就直接报错
- LLM 经常把"用户没填的字段"写成 `null`（比如 `"attractions": null`、`"meals": null`）

**怎么修好的？**
两步：
1. 把所有 `float = 0.0` 改成 `Optional[float] = 0.0`——**声明上就允许 None**
2. 在 `json_parser.py` 加第三次"宽松模式"兜底：`_replace_none_with_defaults()` 按字段名规则（涉及价格/费用的填 `0.0`、涉及列表的填 `[]`）替换 None 后再校验

**验证结果**：
- 之前每次任务必触发 42 个错误
- 修复后第一次直接校验成功
- 任务耗时从 6 分 42 秒降到约 4 分钟

**修改文件**：
- `backend/app/models/schemas.py` 第 196-210 行
- `backend/app/utils/json_parser.py` 第 108-198 行

## 排查清单

下面这些命令是"项目跑不通时怎么定位问题"的标准 SOP。

### LLM 连接检查
**什么时候用**：如果出现"PlannerAgent 卡住"、"LLM 调用失败"等疑似网络/密钥问题。

```bash
cd d:\agent1\backend
.venv\Scripts\python -c "
from app.services.llm_service import get_llm
import asyncio
from langchain_core.messages import HumanMessage
async def test():
    llm = get_llm()
    r = await llm.ainvoke([HumanMessage(content='你好')])
    print(r.content)
asyncio.run(test())
"
```

**预期结果**：1~3 秒内打印出 LLM 的回复（比如"你好！有什么可以帮你的吗？"）。如果超时或报错，检查 `.env` 里的 `DASHSCOPE_API_KEY`。

### 高德 API 检查
**什么时候用**：如果出现"attraction_agent 搜不到景点"、景点都是示例数据等。

```bash
cd d:\agent1\backend
.venv\Scripts\python -c "
from app.agents.tools import search_attractions
import asyncio
result = asyncio.run(search_attractions('湛江', '景点'))
print(f'找到 {len(result)} 个景点')
for r in result[:3]:
    print(f'  - {r.name}')
"
```

**预期结果**：打印"找到 N 个景点"（N >= 5），并列出前 3 个真实景点名（比如"湖光岩"、"赤坎老街"）。

### 后端服务检查
**什么时候用**：前端报"无法连接到服务器"。

```powershell
Get-NetTCPConnection -LocalPort 8000 -State Listen
```

**预期结果**：列出监听 8000 端口的进程（PID）。如果没结果，说明后端没启动。
