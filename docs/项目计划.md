## 0. 一分钟导读（给新来的同学）

如果你第一次看这个项目，先抓住这几条主线：

1. **它是干什么的**——一个能根据用户填的旅行需求，自动生成多日行程的 AI 应用。
2. **核心由 11 个 Agent 节点串起来跑**——IntentAgent 解析需求 → Attraction/Weather/Hotel/Food/RAG 节点并行查信息 → RouteAgent 算路线 → PlannerAgent 用 LLM 生成行程 → BudgetAgent 算账 → FinalizeNode 写库。
3. **用户能提反馈重新生成**——这是项目的核心亮点，详见 [5.7 反馈与重新生成](file:///d:/agent1/docs/项目结构与实现说明.md)。
4. **实际不用 LangGraph 的 `ainvoke`**——改成了**手动顺序 `await` 调用节点**，因为 LangGraph 0.2.x 的 Checkpointing 序列化会卡死（见 [问题排查记录.md 问题 1](file:///d:/agent1/docs/问题排查记录.md)）。但代码里依然按 StateGraph 的 State/Node/Edge 抽象写。
5. **三个核心数据表**——`trip_plans`（行程主表）、`plan_revisions`（版本历史）、`plan_feedbacks`（用户反馈）。看懂了它们的关系就看懂了大半个项目。

详细的目录、文件职责、流程请看 [项目结构与实现说明.md](file:///d:/agent1/docs/项目结构与实现说明.md)；RAG 部分请看 [RAG架构说明.md](file:///d:/agent1/docs/RAG架构说明.md)；改进与踩坑请看 [项目改进计划.md](file:///d:/agent1/docs/项目改进计划.md) 和 [问题排查记录.md](file:///d:/agent1/docs/问题排查记录.md)。

## 1. 项目概述

### 1.1 项目名称
**agent1旅行** — 基于 LangGraph + MCP 的智能多智能体旅行规划助手

### 1.2 项目定位
一个可落地的全栈 AI 应用，覆盖「需求理解 → 信息检索 → 多 Agent 协作规划 → 结果生成 → 可视化展示 → 用户反馈优化」完整链路。

**用人话讲**：用户填一份旅行需求表（去哪、几天、几个人、想玩什么），系统自动生成一份多日行程，并且能根据用户反馈不断修改。

核心区别于原 helloagents-trip-planner：
- Agent 框架从 SimpleAgent 升级为 **LangGraph**（实际改用手动顺序 `await` 调用节点，保留 State/Node/Edge 抽象），引入状态图、持久化记忆、条件分支、反思循环等复杂能力；
- 明确拆分「感知 Agent、检索 Agent、规划 Agent、反思 Agent、预算 Agent」等多个专业 Agent；
- 引入 **RAG 知识库**（城市攻略、景点背景）与 **记忆模块**（用户偏好长期保存）；
- 支持人机协同：关键决策点可暂停等待用户确认；
- 支持行程版本管理与 A/B 对比；
- 增加**用户登录与多用户隔离**，行程/偏好独立存储；
- 增加**攻略爬虫**，自动更新 RAG 知识库；
- 增加**支付/预订沙箱**，展示完整商业闭环。

### 1.3 目标用户
- 需要个性化旅行方案的普通用户；
- 想要展示复杂 Agent 系统设计能力的求职者。

### 1.4 核心价值
1. **多 Agent 分工协作**：每个 Agent 只负责单一专业任务，降低单 Agent 幻觉风险；
   - **通俗讲**：不要让一个 AI 干所有事，让"专才"AI 协作，景点专家搜景点、酒店专家找酒店、规划专家排行程。
2. **状态驱动的图式工作流**：用 LangGraph StateGraph 显式建模规划流程，便于调试、扩展和面试讲解；
3. **工具增强 + 知识增强双驱动**：MCP 获取实时数据，RAG 补充背景知识；
   - **通俗讲**：实时数据（高德 POI、天气）告诉你"现在有什么"，知识库（百度百科）告诉你"它是什么"。
4. **可解释可干预**：用户能看到每个 Agent 的思考与工具调用过程，关键节点可人工介入；
5. **完整商业闭环**：用户系统 + 历史行程 + 收藏 + 支付沙箱，更接近真实产品；
6. **数据自更新**：爬虫持续补充知识库，系统越用越「懂」城市。

## 4. 整体架构

### 4.0 用人话讲架构

整个系统可以想象成一个"餐厅"：
- **用户**（顾客）通过**前端**（服务员）点单（提交需求）
- **后端**（厨房）接到单子后，由**多个 Agent**（不同厨师）分工完成
- 每个 Agent 调用**外部服务**（高德 = 菜场、百度百科 = 食材百科）
- 完成后**数据层**（仓库）记录每一道菜

最核心的特点：
- **顺序编排**——11 个 Agent 节点像流水线一样一个一个跑，每个节点处理一个步骤
- **实时反馈**——SSE 推日志让用户看到"现在做到哪一步了"
- **可重复生成**——用户能提反馈重新生成，保留每次的版本

使用 pydantic-settings，从 `.env` 加载：
- `AMAP_API_KEY`
- `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL_ID`（百炼：`https://dashscope.aliyuncs.com/compatible-mode/v1`）
- `DATABASE_URL`（如 `postgresql+asyncpg://user:pass@localhost/agent1travel`）
- `QDRANT_URL` / `QDRANT_COLLECTION`
- `EMBEDDING_MODEL_NAME`
- `REDIS_URL`（可选）
- `JWT_SECRET_KEY` / `JWT_ALGORITHM` / `JWT_EXPIRE_MINUTES`
- `AGENT_MAX_RETRIES`、`AGENT_TIMEOUT`
- `PAYMENT_SANDBOX`（是否启用支付沙箱）
- `ALIPAY_APP_ID`、`ALIPAY_PUBLIC_KEY`、`ALIPAY_PRIVATE_KEY`（可选）
- `CRAWLER_ENABLED`、`CRAWLER_SCHEDULE`（爬虫开关与定时规则）

### 5.3 服务层职责
- **LLMService**：统一封装 LLM 调用，优先接入百炼 OpenAI 兼容接口；
- **AmapService**：通过 MCP 调用高德地图 POI 搜索、天气、路线规划、地理编码；
- **RAGService**：文档切分、Embedding、向量检索、上下文注入；
- **MemoryService**：用户偏好读写、会话历史、行程版本；
- **AuthService**：用户注册、登录、JWT 签发、密码校验；
- **PaymentService**：沙箱支付订单创建、状态查询、回调处理；
- **CrawlerService**：攻略数据采集、清洗、去重、入库。

- **人工介入**：`human_in_the_loop` 在预算超支时暂停置 `pending_approval`，经 `POST /api/trip/{plan_id}/approve` 审批后断点续跑；
- **地图联动**：点击左侧景点，地图高亮并 InfoWindow 展示详情；
- **拖拽调整**：用户可调整景点顺序，前端调用 `/api/trip/recalculate` 重算路线。

## 7. Agent 系统设计（核心）

### 7.0 一段话讲清楚

把整个 Agent 系统想象成一条**流水线工厂**：
- **IntentAgent** 是"前台接单员"——把用户的需求表（自然语言）翻译成结构化清单（IntentAnalysis）
- **Attraction / Weather / Hotel / Food / RAG 五个 Agent** 是"采购部"——并行去查景点、天气、酒店、餐饮、城市攻略
- **RouteAgent** 是"调度员"——计算景点之间的距离和时间
- **PlannerAgent** 是"主厨"——拿到所有信息后用 LLM 生成最终行程
- **BudgetAgent** 是"会计"——把门票、酒店、餐饮、交通费用算清楚
- **FinalizeNode** 是"打包发货员"——把行程写到数据库，并发一条"完成了"的 SSE 通知

**两个关键事实**：
1. 这些 Agent 节点**按顺序跑**（不是真的"智能分工"），代码里就是 `for node in [a, b, c, ...]: await node(state)`，每跑一个就把结果合并到 `state` 里
2. **用户提反馈重新生成时，跑的是同一套节点**——只是"前台接单员"在 TripRequest 里多塞了一段"本次需要满足的修改意见"

### 7.1 框架选型：LangGraph

#### 为什么选 LangGraph
| 对比项 | hello-agents SimpleAgent | LangGraph |
|--------|--------------------------|-----------|
| 架构能力 | 单 Agent + 简单工具调用 | 多 Agent 状态图编排 |
| 流程控制 | 顺序调用，无显式图 | 节点、边、条件分支、循环 |
| 记忆能力 | 无 | 内置 Checkpointer 持久化 |
| 人机协同 | 不支持 | `interrupt` 节点支持人工确认 |
| 可观测性 | 弱 | 完整 State 快照，便于调试 |
| 面试价值 | 入门 | 工业级复杂 Agent 设计 |

#### LangGraph 核心概念在本项目中的映射
| LangGraph 概念 | 本项目映射 |
|----------------|-----------|
| `StateGraph` | 整个旅行规划工作流 |
| `State` | `TravelPlanningState` 共享状态对象 |
| `Node` | 各个 Agent / 工具节点 |
| `Edge` | Agent 之间的数据流与执行顺序 |
| `Conditional Edge` | 根据工具结果决定下一步 |
| `Checkpointer` | 持久化状态，支持重跑与人机协同 |
| `interrupt` | 用户确认节点 |

### 7.3 Agent 节点详细设计

#### 7.3.1 IntentAgent（意图理解 Agent）
- **职责**：解析用户自然语言输入，提取结构化需求，识别隐含偏好；
- **输入**：`TripRequest` + `rag_context`（可选）；
- **输出**：`IntentAnalysis`（城市、日期、天数、交通、住宿、偏好标签、必去景点、预算区间、特殊需求）；
- **工具**：无（纯 LLM 推理）；
- **关键提示词要求**：
  - 识别用户是否提到「亲子」「老人」「穷游」「美食」等隐含标签；
  - 将 `free_text_input` 转为结构化约束；
  - 输出严格 JSON。

#### 7.3.2 AttractionAgent（景点检索 Agent）
- **职责**：根据城市与偏好检索候选景点；
- **输入**：`IntentAnalysis`；
- **输出**：`List[Attraction]`；
- **工具**：
  - `amap_maps_text_search`：POI 文本搜索；
  - `amap_maps_search_detail`：POI 详情；
- **检索策略**：
  - 按偏好标签发起多次检索（如「历史文化」「美食街」「亲子」）；
  - 去重、过滤无坐标项、按热度/评分排序；
  - 每个景点必须包含真实经纬度。

#### 7.3.3 WeatherAgent（天气查询 Agent）
- **职责**：查询旅行期间天气；
- **输入**：城市、日期范围；
- **输出**：`List[WeatherInfo]`；
- **工具**：`amap_maps_weather`；
- **处理逻辑**：
  - 高德天气返回未来 4 天，若旅行天数更长，则后续日期用历史同期气候补充说明。

#### 7.3.4 HotelAgent（酒店推荐 Agent）
- **职责**：根据住宿偏好和景点区域推荐酒店；
- **输入**：城市、住宿类型、候选景点中心坐标；
- **输出**：`List[Hotel]`；
- **工具**：`amap_maps_text_search`（搜索酒店）；
- **策略**：
  - 先计算景点中心点；
  - 搜索目标区域内酒店；
  - 按距离、价格、评分综合排序。

#### 7.3.5 RAGAgent（知识检索 Agent）
- **职责**：从本地知识库检索城市攻略、景点背景、避坑建议；
- **输入**：城市、偏好、候选景点名称；
- **输出**：`rag_context` 字符串；
- **工具**：向量数据库检索；
- **实现**：
  - 使用 `SentenceTransformer` 生成 query embedding；
  - Qdrant 检索 Top-K 文档片段；
  - 重排序后拼接为上下文。

#### 7.3.6 RouteAgent（路线规划 Agent）
- **职责**：为候选景点规划每日路线，计算距离与通行时间；
- **输入**：候选景点列表、交通方式；
- **输出**：`route_matrix`（景点间路线信息）；
- **工具**：
  - `amap_maps_direction_walking_by_address`
  - `amap_maps_direction_driving_by_address`
  - `amap_maps_direction_transit_integrated_by_address`
- **策略**：
  - 使用聚类算法（K-Means / DBSCAN）按地理位置分组；
  - 同组景点安排在同一天；
  - 组内使用 TSP 近似算法排序。

#### 7.3.7 PlannerAgent（行程规划 Agent）
- **职责**：整合所有信息，生成结构化多日行程；
- **输入**：IntentAnalysis + attractions + weather + hotels + route_matrix + rag_context；
- **输出**：`List[TripPlan]`（2-3 个候选方案）；
- **工具**：无；
- **提示词要求**：
  - 每天 2-4 个景点，考虑路线距离；
  - 根据天气调整室内外景点；
  - 每天包含三餐，午餐靠近景点，晚餐可安排特色街区；
  - 输出严格 JSON Schema；
  - 候选方案需在风格/节奏上有差异（紧凑版、休闲版、省钱版）。

#### 7.3.8 BudgetAgent（预算核算 Agent）
- **职责**：对候选方案进行费用核算与校验；
- **输入**：候选行程；
- **输出**：补全 `Budget` 并标注不确定性；
- **逻辑**：
  - 根据景点票价、酒店均价、餐饮均价、交通距离估算费用；
  - 若总费用超出用户预算区间，触发重新规划。

#### 7.3.9 HumanInLoopNode（人机协同节点）
- **职责**：在需要用户决策时暂停图执行；
- **触发条件**：
  - 多个候选酒店评分接近；
  - 用户明确提到「帮我选一下」；
  - 预算超出用户预期；
- **实现**：使用 LangGraph `interrupt`，前端弹出确认 UI。

#### 7.3.10 FoodAgent（餐饮检索 Agent）★ 实际新增
- **职责**：搜三餐候选餐厅（中餐/西餐/海鲜/快餐等）；
- **输入**：城市、用餐时间、用户偏好；
- **输出**：`List[Meal]` 候选；
- **工具**：高德 POI 搜索 + RAG 补背景。

#### 7.3.11 修订路径节点（重新生成）★ 实际新增

`graph.py` 里除了 `run_planning_graph`（首次规划）外，还有 `run_revision_graph`（基于反馈重新生成），新增 2 个节点：

- **feedback_extractor_node**：
  - 输入：用户 `plan_feedbacks` 表里的多条原始反馈
  - 输出：聚合文本 + 结构化 `StructuredFeedback`
  - 判定 `complexity` 是 `patch`（小改某天）还是 `full`（整体重排）
- **patch_plan_node**：
  - 输入：feedback + 当前 plan_data
  - 输出：只改涉及的天，其他天保留
  - 流程：拉候选 → LLM 重生成那几天 → merge

> 当前 `/regenerate` 接口**默认 force full**（复杂度强制 full），不实际用 patch 路径——但代码保留了 patch 路径实现作为未来选项。

### 7.4 工作流（实际为手动顺序执行）

> **重要**：下面这张图是**按 LangGraph StateGraph 抽象设计**的，但**实际是手动顺序 `await` 调用**（不用 `ainvoke`），原因是 LangGraph 0.2.x 的 Checkpointing 序列化 Pydantic 对象会卡死（见 [问题排查记录.md 问题 1](file:///d:/agent1/docs/问题排查记录.md)）。

#### 实际代码（graph.py 伪代码）

虽然结构图看起来像 LangGraph StateGraph，但**执行层是手写**——`for node in [...]: await node(state)`：

```python
# graph.py → run_planning_graph / run_revision_graph
state = initial_state_from_request(request)
for node in [
    intent_agent_node,        # 1. 解析意图
    attraction_agent_node,    # 2. 搜景点
    weather_agent_node,       # 3. 查天气
    hotel_agent_node,         # 4. 找酒店
    food_agent_node,          # 5. 找餐厅
    rag_agent_node,           # 6. 城市攻略
    route_agent_node,         # 7. 算路线（asyncio.gather 并行）
    planner_agent_node,       # 8. LLM 生成行程
    budget_agent_node,        # 9. 算预算
    human_in_the_loop,        # 10. 人机协同（预算超支暂停审批）
    finalize_node,            # 11. 写库 + 算 diff
]:
    update = await node(state)         # 顺序执行
    state.update(update)
    streaming.publish(plan_id, node.__name__, update)
return state
```

> 节点执行过程中，每一步都通过 `streaming.publish()` 推一条 SSE 日志，前端的 `Planning.vue` 实时显示进度。

#### 条件分支示例
```python
def route_after_budget(state: TravelPlanningState):
    if state["error"]:
        return "reflect_agent"
    if state["intent_analysis"].budget_limit and \
       state["candidate_plans"][0].budget.total > state["intent_analysis"].budget_limit:
        return "human_in_loop"
    return "finalize_plan"
```

- 返回结果中标注信息来源，增强可信度。

### 7.8 反思与自优化

#### 7.8.1 反思触发时机

- `BudgetAgent` 发现预算超支；

#### 7.8.2 反思逻辑

class ReflectAgent:
    def run(self, state: TravelPlanningState):
        feedback = state["feedback"]

        # 2. 生成改进建议
        # 3. 更新用户偏好
        # 4. 决定是否重跑某节点

### 7.9 异常处理与兜底

| 异常场景 | 处理策略 |
|----------|----------|
| MCP 工具超时 | 重试 2 次，失败后使用缓存/占位数据 |
| LLM 返回非 JSON | JSON 修复 Agent / 兜底 JSON 模板 |
| 景点数量不足 | 放宽搜索关键词，扩大检索范围 |
| 预算超支 | 调用 ReflectAgent 重新选择低价酒店/景点 |
| 用户未响应人机协同 | 默认选择第一个选项并继续 |

### 7.10 爬虫与数据更新设计

#### 7.10.1 爬虫目标

```

#### 7.10.4 更新策略
- 初次部署时全量抓取；
- 后续通过 APScheduler / Celery 定时增量更新；
- 对热门城市提高更新频率（如每周一次）。

### 7.11 支付与订单设计

#### 7.11.1 设计原则
- 先接入**沙箱环境**，不触碰真实资金；
- 订单与行程计划绑定，用户可对某个方案发起「预订」；
- 支付成功后仅更新订单状态，不真正出票/订房。

#### 7.11.2 订单状态机
```
pending → paid → confirmed
   ↓        ↓
cancelled  refunded
```

#### 7.11.3 沙箱接入方式
- **支付宝沙箱**：使用支付宝开放平台提供的沙箱 APPID、公钥、私钥；
- **微信支付沙箱**：使用微信支付的沙箱环境；
- 前端展示二维码或模拟支付按钮，后端接收回调。

#### 7.11.4 安全注意
- 密钥不存入代码，全部走环境变量；
- 回调接口做签名验证；
- 金额、订单号等关键字段防篡改；
- 面试时强调「这只是沙箱演示，真实生产需要资质和合规审查」。

@router.get("/agent/trip/{plan_id}/stream")
async def stream_agent_events(plan_id: str, token: str = ""):
    """SSE 实时推送 Agent 执行日志"""
    async def event_generator():
        # 1. 先发历史日志（断线重连时也能拿到）
        for log in streaming.get_history(plan_id):
            yield f"data: {json.dumps(log, ensure_ascii=False)}\n\n"

        # 2. 实时订阅新日志
        async for log in streaming.subscribe(plan_id):
            yield f"data: {json.dumps(log, ensure_ascii=False)}\n\n"
            if log.get('type') in ('completed', 'failed'):
                break

    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

@router.post("/trip/{plan_id}/regenerate")
async def regenerate_plan(plan_id: str, ...):
    """根据所有反馈重新生成行程"""
    # 1. 互斥锁检查（per-plan）
    if _is_revision_running(plan_id):
        raise HTTPException(400, "行程正在修订中，请等待完成")

    # 2. 聚合反馈
    aggregated_notes, feedbacks = await memory_service.aggregate_active_feedbacks(
        session, plan_id
    )

    # 3. 构造新请求（注入反馈）
    trip_request = original_request.model_copy()
    trip_request.free_text_input = (
        f"{original_request.free_text_input}\n\n"
        f"【本次重新生成需要满足的修改意见】\n{aggregated_notes}"
    )

    # 4. 强制 full 路径
    force_full = StructuredFeedback(complexity="full", scope="whole", ...)

    # 5. 后台启动
    task = asyncio.create_task(_run_revision_task(plan_id, trip_request, force_full))

    return {"success": True, "status": "revising", "plan_id": plan_id}
```

## 11. 项目亮点 / 面试卖点

### 11.1 架构层面
1. **从简单 Agent 升级到 LangGraph 状态图**：能清晰讲解 Node、Edge、State、Checkpointer 的关系；
2. **多 Agent 分工协作**：每个 Agent 职责单一，便于调试和扩展；
3. **并行信息收集**：Attraction / Weather / Hotel / RAG 并行执行，减少延迟；
4. **持久化状态与人机协同**：使用 LangGraph Checkpointer 实现断点续跑和用户确认。

### 11.2 技术层面
1. **MCP 协议实战**：通过标准 MCP 接入高德地图，工具可插拔；
2. **RAG + Tool Use 双增强**：既有实时数据，又有背景知识；
3. **记忆系统**：用户偏好长期保存，支持个性化推荐；
4. **反思机制**：根据反馈持续优化规划策略。

### 11.3 工程层面
1. **用户系统与多租户隔离**：JWT 认证 + SQLAlchemy 用户/行程/偏好分离；
2. **结构化输出 + 严格校验**：所有 Agent 输出均用 Pydantic 校验；
3. **异常降级**：工具失败、LLM 输出异常均有兜底方案；
4. **可观测性**：完整 Agent 执行日志，支持前端实时展示；
5. **版本管理**：同一请求生成多个候选方案，支持对比；
6. **数据闭环**：爬虫 → 清洗 → Embedding → RAG 检索 → 用户反馈 → 持续优化。

 │            │<─TripPlanResponse + version=1 + diff_summary=null──│              │                    │
 │<─看结果 + 反馈按钮─────────│             │              │                  │                    │
```

**关键点说明**：
- **`POST /api/trip/plan`** 是同步入口，但**规划任务是 `asyncio.create_task` 后台跑**，立刻返回 `plan_id`；前端再开 SSE 连接
- **SSE 同时支持**"先发历史日志 + 再推实时日志"——断线重连也能拿到完整过程
- **`finalize_node` 才写库**——前面所有节点失败都不污染数据库
- **`diff_summary=null`**——首次规划没有"上一版"可比

**关键点说明**：
- **不立刻启动任务**：用户可能还要继续提意见，提 N 条都只入库，不消耗 token
- **强制 full 路径**：`complexity="full"` 不走 patch 路径，整体重排更稳定
- **per-plan 互斥锁**：`_revision_locks[plan_id]` + `_revision_running[plan_id]` 防止并发
- **完整 page refresh**：SSE 完成后用 `window.location.href`（不用 `router.push`），绕开 Vue Router 复用组件的坑
- **`diff_summary` 关键**：前端能展示"本次修改了 N 处"，否则用户感知不到变化

### 关系速记

- `User 1 ──── N TripPlan`（一个用户多个行程）
- `TripPlan 1 ─ N PlanRevision`（一个行程多个版本，v1/v2/v3，**`is_current=1` 才是当前版本**）
- `TripPlan 1 ─ N PlanFeedback`（一个行程多条反馈，`is_withdrawn=0` 才有效）
- `PlanRevision 1 ─ N PlanFeedback`（一条反馈可能引用某个版本作为"针对哪个版本的反馈"）
- `User 1 ── 1 UserPreference`（每个用户一套偏好）
- `User 1 ── N UserMemory`（每个用户多条事件级记忆）

### 关键设计

- **plan_revisions 是项目核心数据**——所有"重新生成"都新建一行 revision，旧版 is_current=0
- **plan_feedbacks 不级联删除**——用 `is_withdrawn` 软删除，撤回后历史仍可见
- **user_memories 用于"事件级"记忆**——比如"用户 7 月 1 日对湛江的某个景点点了赞"，颗粒度比 user_preferences 细
